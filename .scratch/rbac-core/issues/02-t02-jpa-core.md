## What to build

在原仓库的独立整改数据库中，用一组小样例通过 JPA 保存并读回“部门—人员—角色—权限—API”完整数据链，为业务切片提供共同基础。

## Acceptance criteria

- [ ] 复用现有 Java、Spring Boot、MySQL 与构建骨架，加入所需 JPA 支持；不新建替代项目，不一次性重写全部 Service。
- [ ] 按已确认模型建立实体及三组关联关系；联合唯一性、必要外键、系统归属和树约束有持久化或领域规则验证，不能只画图。
- [ ] 用小样例验证多角色、无角色、同 API 被多个权限引用、部门父子及权限父子；这些是测试数据，不是未经评审的正式 API 清单。
- [ ] 整改库与原库隔离，启动或测试不会让旧初始化器向新模型写入旧目录，也不会修改原库；保留 MySQL 驱动和必要工程依赖。
- [ ] 记录与原实现共存/集成的边界；旧调用尚未迁移时不提前删除其共享实现。没有新增正式 Controller 或产品页面。

## 共享模块及冲突

构建依赖、实体与关联、建库和启动初始化、测试数据入口。与 T03/T05/T07/T09/T11 的数据改动可能冲突，先稳定共同映射再各自迁移。

- 开始前阅读[整改执行入口](../../../docs/rbac-rectification/RBAC整改执行入口.md)，逐项核对本票阻塞项和评审证据。
- 只执行用户指定的本票；在独立分支或工作树修改，保护已有未跟踪文档。
- 验收项是未来完成条件，全部保持未勾选；拆票获批不等于设计评审或运行验收通过。
- 按交付类型保留原型/契约评审、数据库/HTTP/并发等相应证据；记录实际未验证项。正式前端仍暂缓。
- 提交本票变更供小组评审；前置票的结论与所需产物进入共同基线后，下游才可开始。不得自行合并或顺带认领下游。

## What to build

小组可复现“登录身份—部门人员—角色授权—真实 API 放行/拒绝”的当前后端结果，并明确哪些要求尚未完成。

**阻塞原因：**要验证的是清理并切换后的当前后端，不能以旧功能尚在的中间状态替代完成。

## Acceptance criteria

- [ ] 在干净整改库及实际组织人员数据上重走约定链路，保留 Java/MySQL、真实 HTTP 和重要事务/并发结果；旧测试报告不作新结构证据。
- [ ] 验证约一万人下分页、总数、搜索及部门筛选，不泄漏范围外数据；没有约定性能指标时如实记录环境与结果，不虚报吞吐或响应时间。
- [ ] 跨资源/映射、角色权限、人员角色/状态三类写入口核对最新授权与最后有效管理员保护，包含交叉并发与回滚，不只测各票的成功样例。
- [ ] 对照原型/API 契约，核对输入输出、错误和权限范围；核对 JPA、AOP 和 Controller/Service/Repository 职责，确认旧 JDBC/错误模型未在保留路径继续使用。
- [ ] 同步验收说明、初始化说明、已知限制与 PR 变更范围，分别标注“当前后端已验证”“正式前端暂缓”“课程系统未完成”；不自行合并。
- [ ] 本票通过只代表当前 RBAC 后端阶段通过，不代表界面或双系统要求已经验收。

## 共享模块及冲突

全部保留接口、测试数据、集成/并发验证、配置和交付说明。不得用修报告代替修实现；发现缺陷回到相应业务票修正。

## 开始与完成

- 开始前阅读[整改执行入口](../../../docs/rbac-rectification/RBAC整改执行入口.md)，逐项核对本票阻塞项和评审证据。
- 只执行用户指定的本票；在独立分支或工作树修改，保护已有未跟踪文档。
- 验收项是未来完成条件，全部保持未勾选；拆票获批不等于设计评审或运行验收通过。
- 按交付类型保留原型/契约评审、数据库/HTTP/并发等相应证据；记录实际未验证项。正式前端仍暂缓。
- 提交本票变更供小组评审；前置票的结论与所需产物进入共同基线后，下游才可开始。不得自行合并或顺带认领下游。

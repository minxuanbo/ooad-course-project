通过原型确认组员如何核对菜单/按钮树、系统归属和真实 API 映射，只为确有使用场景的操作制定契约。

## Acceptance criteria

- [ ] 原型能说明一个菜单/按钮对应哪些 API，以及同 API 被多个权限复用的含义；明确系统、方法和路径模板的展示。
- [ ] 逐项确认本轮实际需要的查询、映射保存和必要维护/停用操作；没有场景支持的实体全套 CRUD 不进入契约。
- [ ] 覆盖树循环、按钮有子节点、跨系统关联、重复关系、未授权修改和关键管理资源变更的拒绝反馈。
- [ ] 审核根部门成员还须拥有对应操作权限的条件，以及会影响最后有效管理员时的处理；不新增管理员字段。
- [ ] 仅选择本权限系统实际需要的目录；课程侧接口仍待后续场景确认。形成逐项评审记录，正式前端继续暂缓。

## 共享模块及冲突

资源术语、权限树、映射 DTO、全局维护与停用语义。与 T08 角色选权原型共享权限树表现，需协调但不强制串行。

## 开始与完成

- 开始前阅读[整改执行入口](../../../docs/rbac-rectification/RBAC整改执行入口.md)，逐项核对本票阻塞项和评审证据。
- 只执行用户指定的本票；在独立分支或工作树修改，保护已有未跟踪文档。
- 验收项是未来完成条件，全部保持未勾选；拆票获批不等于设计评审或运行验收通过。
- 按交付类型保留原型/契约评审、数据库/HTTP/并发等相应证据；记录实际未验证项。正式前端仍暂缓。
- 提交本票变更供小组评审；前置票的结论与所需产物进入共同基线后，下游才可开始。不得自行合并或顺带认领下游。

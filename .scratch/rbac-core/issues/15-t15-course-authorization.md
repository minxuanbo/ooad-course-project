## Acceptance criteria

- [ ] 仅实现或对接 T14 审核通过的最小课程操作，登记实际课程 API；沿用既有工程/对接边界，不复制另一套 RBAC 或新造完整课程系统。
- [ ] 课程受控请求实际进入授权检查；有权成功、无权拒绝可复现，不能用两条系统记录、菜单可见或模拟鉴权响应替代。
- [ ] 通过已完成的角色配置和人员角色修改，演示权限系统与课程系统的访问结果前后变化，以及跨系统错误映射的拒绝；后续请求使用最新有效授权。
- [ ] 按 T14 已确认的范围验证课程业务条件，不擅自把人员部门范围扩成新的课程数据权限需求。
- [ ] 同步真实 HTTP/联调证据、必要初始化、测试和文档；正式前端仍按另行确认的范围处理，不能宣称课程界面已验收。
- [ ] 与 T13 的当前后端证据合并核对后，才能讨论双系统整体要求是否通过；任一项未完成都保留待办状态。

## 共享模块及冲突

多系统资源、真实 API 拦截、角色配置、人员角色及联调数据。与 T07/T09/T11 共享授权规则；如后续修改当前后端公共行为，须回归对应切片与 T13 场景。

## 开始与完成

- 开始前阅读[整改执行入口](../../../docs/rbac-rectification/RBAC整改执行入口.md)，逐项核对本票阻塞项和评审证据。
- 只执行用户指定的本票；在独立分支或工作树修改，保护已有未跟踪文档。
- 验收项是未来完成条件，全部保持未勾选；拆票获批不等于设计评审或运行验收通过。
- 按交付类型保留原型/契约评审、数据库/HTTP/并发等相应证据；记录实际未验证项。正式前端仍暂缓。
- 提交本票变更供小组评审；前置票的结论与所需产物进入共同基线后，下游才可开始。不得自行合并或顺带认领下游。

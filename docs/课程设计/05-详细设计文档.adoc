== 文档目的与阅读约定

本文定义系统的组件职责、接口协议、数据传递、授权算法、状态转换、事务边界、界面协作和验证准则，作为开发、联调与设计评审的依据。阅读本文不要求另行阅读独立 API 说明。
数据库实体、字段、键、索引及 SQL 定义由配套《数据库设计文档》规定；本文包含业务与数据访问规则，两份文档共同构成设计交付。
文中的标识符、类名和路径属于设计契约；JSON 示例使用虚构值，只说明格式，客户端应使用查询接口提供的实体 ID。


[cols="1,4",options="header"]
|===
|术语 |定义
|业务权限 |外部业务系统的“功能点＋动作”访问许可，由用户角色与角色权限关系求并集。
|管理操作 |本权限平台人员、组织、角色、审计和离职操作的能力码。
|管理范围 |员工所持某一角色可管理的组织集合；与该角色的管理操作共同构成有效授权。
|平台管理员 |启用的系统管理员角色持有者，且相关管理操作具有 GLOBAL 范围；不是仅凭岗位名判断。
|鉴权与执行业务 |/authorize 只返回许可判断，业务系统负责其自身事务执行。
|可空／可省略 |可空表示 JSON null 合法；可省略表示请求可不带该字段，两者不自动等价。
|幂等 |重复请求的资源状态一致；不保证只产生一条审计事件。
|===

== 总体结构与组件协作

系统采用前后端分离、单一后端应用和关系数据库。前端通过 JSON HTTP 接口调用后端；离线原型独立模拟交互。授权决策位于后端，界面状态不作为授权依据。

[source,text]
----
Vue 页面 → API 客户端 → RequestAuditFilter
                         ↓
                Controller（HTTP 绑定）
                         ↓
       Service（业务规则、事务、DTO 组装）
             ↔ AuthService / ManagementAccess
                         ↓
              Repository（参数化 SQL）
                         ↓
                  MySQL（约束与持久化）

成功响应 → ApiResponseAdvice → {code,message,data,requestId}
异常响应 → ApiExceptionHandler → HTTP 状态＋稳定业务错误码
认证事件 → AuditRecorder（独立事务）→ authorization_logs
----


[cols="1,3,3",options="header"]
|===
|模块 |入口与主要协作 |读写边界
|认证与个人门户 |ApiController → ApplicationService → AuthService／AuthRepository |会话建立和撤销；个人身份、角色、有效权限。
|人员、业务角色和目录 |ApiController → ApplicationService／ApplicationRepository |人员范围查询、角色集合替换、角色业务权限、应用准入与操作判断。
|组织与管理授权 |ManagementController → ManagementService／ManagementRepository |公司部门维护、角色管理操作、员工角色及范围原子替换。
|审计 |AuditController → AuditService／AuditRepository；RequestAuditFilter → AuditRecorder |日志筛选、游标、批量归档与认证事件持久化。
|初始化 |DatabaseConstraints → DataInitializer／ExcelXmlReader／RolePolicy |先建约束，再在空库事务导入默认数据。
|===
== 系统目标与功能边界

设计统一登录、业务 RBAC0、细粒度后台管理、公司／部门范围、离职集中撤权及审计。
业务系统以应用、模块、功能点、动作为权限目录，提供准入与功能鉴权演示，不代替真实业务系统执行操作。
HR 增量同步、OA 流程联动、SSO、角色继承和互斥角色不在本阶段范围。

管理策略由“角色的操作权限 + 员工该角色的组织范围”共同决定。
角色目录采用系统管理员、公司领导、部门经理、项目经理、普通员工五类角色。
部长和副部长使用部门经理；项目经理、项目副经理、项目总工程师使用项目经理。
管理操作直接配置给上述角色。公司范围覆盖所属全部部门，部门范围只覆盖选定部门／项目部。

== 分层与组件职责

[cols="1,3",options="header"]
|===
|层／组件 |职责与依赖
|Controller |ApiController、ManagementController、AuditController 仅绑定路径、参数、请求 DTO 并调用 Service；不执行 SQL 或制定业务规则。
|Service |ApplicationService 负责人员、角色、目录、鉴权及离职事务；ManagementService 负责组织及角色范围配置；AuditService 负责日志筛选、游标和归档；AuthService 负责认证会话；ManagementAccess 统一权限及范围规则。
|Repository |ApplicationRepository、ManagementRepository、AuditRepository、AuthRepository、ManagementAccessRepository 封装 JdbcTemplate 和参数化 SQL；不直接读取 HTTP 请求，不组装 HTTP 响应。
|DTO |Requests 声明登录、鉴权、角色、范围、组织、离职输入；Responses 声明个人资料、人员、角色、目录、组织和交接输出；AuditDtos 声明查询、游标页、归档输入输出。DtoMapper 将内部 SQL 投影转换为显式响应记录。
|ApiResponse / Advice |所有成功响应包装为 code、message、data、requestId，写操作 data=null；集合在 data 内。HTTP 层一次包装，已包装错误不重复包装。
|ApiExceptionHandler |业务错误按稳定 code 与 HTTP 状态映射；参数 400、认证 401、权限 403、资源 404、方法 405、约束冲突 409、未知内部异常 500。
|RequestAuditFilter / AuditRecorder |生成请求 ID，捕获登录及 API 401/403；独立事务记录认证事件，不写密码、令牌、请求体或查询串。
|DatabaseConstraints |在导入前建立部门负责人外键和登录唯一标识触发器；不改写既有业务数据。
|DataInitializer / ExcelXmlReader / RolePolicy |事务导入 Excel，校验源数据、映射现有角色并一次性配置管理权限和范围。
|Vue / 离线原型 |Vue 使用统一响应和业务错误码；HTML 原型模拟交互，不调用真实服务。
|===

请求依赖方向为 Controller → Service → Repository → MySQL。业务服务复用 AuthService、ManagementAccess；Repository 不反向依赖服务层。
Service 在写事务内重新检查规则；Controller 不负责事务。Repository 返回内部查询投影，Service 组装 DTO，外部不直接消费 JDBC Map。
SQL 范围片段只来自固定列名、已校验权限码和数值 ID；外部筛选值用占位参数。READ COMMITTED 下每次读取最新权限，不信任客户端权限快照。

== 数据模型

业务域为 users → user_roles → roles → role_permissions → permissions → features → modules → applications；
actions 描述动作种类。启用的用户、角色、权限、功能点、模块、系统及动作共同决定有效业务权限。

管理域为 roles → role_management_permissions，以及 user_roles → management_scopes。
员工范围含 user_id、role_id、scope_type、company_id、department_id；通过复合外键绑定员工已有角色。
DEPARTMENT 范围只保存 department_id，其公司在查询时派生；COMPANY 仅保存 company_id，GLOBAL 不存组织。login_identifiers 维护跨字段登录唯一空间。
管理写事务统一锁定 roles 中 code=系统管理员的固定角色行，串行核验授权与最后管理员约束。
详细字段和 SQL 见 link:04-数据库设计文档.adoc[数据库设计文档]。

== 初始化设计

. schema.sql 建立最终的 18 张表、索引和声明式约束。DatabaseConstraints 补充循环外键与登录标识触发器。
. DataInitializer 仅在 users 为空且初始化开关启用时，在同一事务中导入三份 Excel 和默认授权。
. 公司与部门先建立；人员据部门归属公司；负责人名称必须唯一匹配。部门无父节点，源父名称只作输入完整性校验。
. 建立五类业务角色和初始管理员，导入应用／模块／功能／动作／权限及角色关联。
. RolePolicy 优先识别项目经理、项目副经理、项目总工程师，再识别公司领导，最后识别部长／副部长及部门负责人；其余为普通员工。业务员工保留普通员工基础角色。
. 为角色设置默认管理操作，为员工角色设置默认公司／部门／全平台范围；验证有效平台管理员。
. 任一步骤失败，导入事务整体回滚；非空库启动跳过导入，不覆盖人工修改或恢复已撤销权限。

默认系统管理员有全部 11 项管理操作；公司领导有人员查询／角色分配、角色查看、组织查看／维护、系统目录查看、离职发起／完成；部门经理和项目经理相同但默认无组织维护；普通员工默认无管理操作。
系统管理员默认 GLOBAL，公司领导默认所属 COMPANY，部门经理／项目经理默认所属 DEPARTMENT。此后显式范围设置可独立于本人所属组织。

Excel 只读导入。建表和约束建立先于导入事务，MySQL DDL 不具有业务 DML 的整体回滚保证。

== 认证与会话

登录通过 login_identifiers.identifier 查询唯一用户；三种标识由数据库触发器在用户写事务中登记，不同用户跨字段冲突时整体回滚。
用户必须 ACTIVE 且 BCrypt 校验成功。服务生成 32 字节随机令牌并以 URL-safe Base64 返回，
数据库只保存 SHA-256 摘要和到期时间，默认 12 小时。

每次请求验证 Bearer 格式、会话未撤销、未过期、用户启用；退出标记当前会话撤销。
账号停用时，即使令牌尚未到期也应拒绝。令牌中不存权限列表，授权修改无需重新登录即可影响后续请求。

== 业务鉴权算法

有效权限取有效角色权限并集，用 EXISTS 避免多角色重复计数。
应用准入要求至少一个该应用的有效权限；功能操作要求权限编码与应用编码相匹配。
功能点允许展示操作目录，但每个按钮携带实时 allowed，拒绝的按钮不可操作。

POST /authorize 返回 allowed，不执行实际业务。系统准入和功能鉴权均写 authorization_logs，记录主体、应用、
权限、结果、原因、事件类型和请求标识。目录改名不会自动改变权限主键；停用任一目录节点会使对应授权失效。

== 管理鉴权算法

管理权限包括人员查询、用户角色分配、角色查看、角色权限配置、组织查看、组织维护、系统目录查看、审计日志查看、
离职发起、离职完成及管理授权配置。完整权限码与接口矩阵见本文“接口契约”章节。

对目标人员执行操作 P 时：

. 验证操作者会话及启用状态。
. 联表查找操作者已分配且启用角色中 permission_code=P 的管理权限，关联该员工同一角色的范围。
. GLOBAL 匹配所有人员，含无部门人员。
. COMPANY 匹配目标部门所属公司；DEPARTMENT 只匹配目标部门，不递归查询。
. 必须存在同一条授权同时满足操作与范围，不能分别合并权限列表和范围列表后求笛卡尔积。
. 再执行管理账号保护、业务角色子集检查、人员状态检查等操作特有条件。

人员列表、total、筛选项、工作台与角色关联人数使用对应权限的同一范围谓词；鉴权日志仅 GLOBAL audit.read 查询全平台记录。
公司／部门筛选只是在授权范围上附加条件。范围外详情／写入对局部管理员统一拒绝，避免用 id 探测越界人员。
角色和应用目录是全平台共享元数据；角色关联人数是人员数据，必须按 role.read 范围过滤。

只有 GLOBAL role.permissions 可修改共享业务角色权限；只有 GLOBAL management.grant 可修改管理授权。
局部管理员不能修改自己的业务角色，不能修改任何管理授权持有者的角色或为其办理离职。
局部角色分配要求目标已有角色及提交角色的所有业务权限均为操作者当前有效业务权限的子集，
避免通过分配更强角色扩大权限。保留角色的范围不变，撤销角色级联撤销其范围；新增角色没有范围，因此不能通过普通角色分配接口额外授予管理范围。

== 角色管理权限与员工范围编辑

角色页面有“业务功能权限”和“管理操作权限”两个入口，均要求 GLOBAL role.permissions。
管理操作列表全量替换，影响此角色所有持有者，员工角色范围保持不变。
audit.read、role.permissions、management.grant 仅系统管理员角色可拥有；运行时还要求该角色 GLOBAL 范围。

人员页面“分配角色与管理范围”需要 GLOBAL management.grant。提交 roleIds 和 scopes 两个数组，范围最多 200 条。
每条范围必须绑定已选择的启用角色；GLOBAL 不带组织，COMPANY 仅带公司，DEPARTMENT 同时带公司和部门且归属一致。
系统管理员只允许 GLOBAL，其他角色只允许 COMPANY 或 DEPARTMENT；完全相同范围去重。

事务锁定系统管理员角色行后校验操作者、目标及全部输入；增量替换角色、重建范围、检查最后管理员、写 SET_ROLE_ASSIGNMENTS 后提交。
失败全部回滚；无范围时业务功能授权仍可生效，但该角色没有管理权限。
最后管理员必须为 ACTIVE，拥有启用的系统管理员角色、该角色的 management.grant 及 GLOBAL 范围。

== 组织维护

GET /organizations 返回 org.read 范围内公司及部门，部门 writable 由 org.write 独立计算。
公司新增与改名仅允许 GLOBAL org.write；部门新增要求对应公司的 COMPANY 或 GLOBAL org.write，
组织模型只有公司与部门；parentId 非空请求会被拒绝，范围不递归。拥有 org.write 的部门范围管理员仅维护已有范围内部门名称和编码。

不开放删除、移动、修改父节点、修改公司归属、停用组织或负责人调整接口。
新增部门必须指定已有公司。组织改名保持 id 不变，原有管理范围仍然有效。
公司、部门编码和名称的唯一性由数据库约束保护，异常通过统一错误处理返回。

== 业务角色编辑

用户角色替换先检查 user.roles、目标组织范围、管理账号保护及权限子集，再锁定目标用户，拒绝已离职人员。
仅删除取消的 user_roles（级联撤其范围），插入新增角色，保留仍选角色及范围，写 SET_ROLES。不存在的 id 不建立关联。

角色权限替换检查 GLOBAL role.permissions，替换 role_permissions 并写 SET_PERMISSIONS。
角色目录全平台共享，不能授权公司管理员局部修改共享角色定义，否则会影响其他公司。
角色采用全平台共享模型；编辑协议不设置版本条件头，合法管理员顺序保存采用最后一次提交。

== 离职状态机

EMPLOYED 为无交接记录的派生状态；HANDOVER 表示交接中；DEPARTED 表示处置完成。

发起时要求 handover.start、目标范围及保护规则通过，禁止处理自己；目标启用且无交接记录。
接收人／负责人必须启用、尚未进入交接、不是离职本人且在同项操作授权范围内。
校验预计日期、说明和 OA 单号，新增 HANDOVER，写 BEGIN_HANDOVER。
该过程不撤销原业务角色或管理授权，也不向接收人自动授予权限。

完成时要求 handover.complete、目标范围及保护规则通过，禁止处理自己。
锁定用户和交接记录；已 DEPARTED 时直接成功；否则要求明确确认和完成说明。
同一事务内撤销全部业务角色和管理授权、保留最后平台管理员、停用账号、撤销全部会话、
写完成记录及 COMPLETE_HANDOVER 审计。保留人员及历史，不物理删除。

交接详情需要 user.read。若关联接收人／负责人已在当前查看范围外，其姓名显示“范围外人员”，工号和 id 隐去。
管理授权配置明细仅向 GLOBAL management.grant 查看者开放，避免通过交接历史泄露其他管理范围。

== 并发与安全边界

所有管理写事务首先锁 roles 中 code=系统管理员的固定行，再检查当前操作权限；随后按需锁目标用户与交接记录。
统一锁将撤权、角色修改、组织维护和离职串行化，确保等待中的写入会按提交后的授权重新判断。
读请求使用当前已提交数据；已完成鉴权的外部在途业务操作不能保证被中断。

SQL 参数化、防越界校验、平台管理者保留约束及审计均由后端负责。
前端隐藏菜单和禁用按钮只用于交互反馈，不构成安全边界。
审计日志仅系统管理员读取全平台记录，包括无法关联当前用户的历史记录。
通用用户新增、删除、密码重置和组织调动不属于系统接口范围。

== 界面协作

Vue 登录后读取 /me。managementGrants 为角色操作与员工角色范围联表计算的派生结果；导航映射具体权限，不用 canManage 一次性放开全部页面。
菜单依次为：我的应用、工作台、组织管理、用户与授权、角色与权限、业务系统、鉴权日志；按当前授权过滤。
组织管理显示“公司—部门—操作”，不显示上级部门或上级公司列。

员工配置弹窗分为“① 分配角色”和“② 设置管理范围”。“添加范围”产生草稿行，范围角色只能选上方已分配角色；同一角色可有多行。
公司范围只显示公司选择；部门范围显示公司和该公司下的部门；全平台不显示组织选择。
切换范围清除不适用字段，切换公司清除部门，撤销角色移除其草稿范围。
所有添加、移除及角色勾选统一在“保存全部更改”时提交，取消丢弃草稿。

管理授权变化后卸载旧视图并重新加载，无当前页面权限则返回我的应用；每三秒及窗口聚焦刷新身份状态。
离线原型提供系统管理员、普通员工、公司领导、部长／副部长、项目经理／项目副经理／项目总工程师的虚构示例，均使用现有五种角色，不连接真实后端。


[[interface-contract]]
== 接口契约

=== 公共协议

统一路径前缀为 `/api`。请求与响应使用 UTF-8 JSON；携带请求体时使用 `Content-Type: application/json`。路径 ID 为有符号 64 位整数，客户端以服务器返回的正 ID 发起业务操作，不推测连续编号。
接口不提供 URL 版本段、ETag、If-Match、幂等键或 JSON Patch 指令数组。PATCH 使用普通字段对象，仅支持规定字段。
所有正常操作返回 HTTP 200，包括新增、退出和无返回值的写操作；不使用 201 或 204。认证、参数、权限与资源错误按错误码表处理。

[source,json]
----
{"code":"OK","message":"成功","data":null,"requestId":"00000000-0000-4000-8000-000000000001"}
----

`requestId` 是服务端生成的 UUID，与 `X-Request-Id` 响应头相同。客户端的 `/authorize` 请求体 `requestId` 是独立业务跟踪号，回显在 `data.requestId` 并写该鉴权事件；不得与外层服务端请求号混为一谈。
认证与应用准入事件使用服务端请求号。通用鉴权事件的 HTTP 方法／路径可为空、状态可为 null；不能由这些字段推断所有事件均来自同一条采集路径。
GET 无请求体。除登录和可无令牌的退出外，均要求 `Authorization: Bearer <token>`；Bearer 前缀大小写及空格按此格式匹配。
SQL 日期时间按 UTC 解释。日志 occurredAt 使用不带时区后缀的本地日期时间字符串（语义为 UTC），archivedAt 和交接时间可能使用空格分隔；客户端不得假设所有时间字段具有相同字符串外观。查询时间参数使用带 Z 的 ISO-8601，预计交接日期为 YYYY-MM-DD。
所有集合响应位于 data 内；空集合返回 []，无交接记录返回 handover=null；内部 DTO 中不适用于该查询投影的可选属性可返回 null。

=== 认证与授权规则

登录使用用户名、工号或手机号及密码。密码采用 BCrypt；会话令牌只在登录响应返回，数据库保存 SHA-256 摘要。除登录、允许无令牌的退出外，接口要求 `Authorization: Bearer <token>`；会话有效期默认 12 小时。

角色决定业务功能权限和管理操作权限；每名员工的角色分配另绑定公司／部门范围。管理鉴权必须通过同一个 roleId 连接角色管理操作与员工范围，不能把不同角色的操作和范围交叉组合。`canManage` 只表示存在有效管理授权，不能代替具体操作检查。

角色目录定义五类角色：系统管理员、公司领导、部门经理、项目经理、普通员工。部长／副部长映射为部门经理；项目经理／项目副经理／项目总工程师映射为项目经理。岗位是初始化依据，之后由管理员显式修改；不另设审计员等角色。


[cols="1,1,1",options="header"]
|===
|范围 |约束 |覆盖目标
|GLOBAL |仅系统管理员角色；companyId、departmentId 均为空 |全平台，包括无部门人员
|COMPANY |非系统管理员角色；companyId 必填，departmentId 为空 |所选公司全部部门及人员
|DEPARTMENT |非系统管理员角色；公司、部门必填且归属一致 |精确指定部门／项目部，不递归扩展
|===


角色可绑定多个范围。没有范围时，该角色的业务功能权限仍生效，但不产生后台管理权。范围只约束本权限平台的管理操作，不代表外部业务系统内部数据权限。

局部管理员不能修改自己的业务角色，也不能调整任何持有管理授权人员的角色或为其办理离职。局部角色分配还要求目标已有角色及提交角色的全部权限均为操作者当前有效业务权限的子集；否则拒绝整次修改。全平台 user.roles 可处理这些目标，但不会因此获得管理授权配置权。

所有管理写事务先锁定 roles 中 code=系统管理员的固定角色行，再重新校验授权和范围。授权替换、组织维护、角色变更及离职处理共用此锁，避免撤权与写入并发越权。最后一名启用且拥有 GLOBAL management.grant 的人员不得被撤销该权限或完成离职。

=== 请求与响应契约

==== 登录、自身信息与业务鉴权

登录请求：`{"account":"账号","password":"密码"}`。账号或密码为 null、账号超过 100 字符或密码超过 200 字符返回 400；账号去除首尾空格后查询，空字符串按凭据不匹配处理；账号不存在、密码错误或停用账号返回 401/LOGIN_FAILED。用户名、工号、手机号在数据库统一命名空间中跨字段唯一；同人多个字段同值允许，不同人不允许占用同一值。

`GET /me` 中 managementGrants 为数组，每项含 id、roleId、roleName、permission、scope、companyId、departmentId、company、department；由当前角色权限和员工角色范围联表计算。无组织字段为 null。permissionCount 是原始角色关联权限数，不代表有效可操作数量；有效业务权限请用 `/me/permissions`。

`POST /authorize` 请求：`{"appCode":"系统码","permissionCode":"权限码","requestId":"跟踪号"}`。appCode/requestId 最多 191 字符，permissionCode 最多 512。返回 `allowed` 布尔值、permissionCode、requestId。没有权限时本接口仍为 200/allowed=false；这只是鉴权结果，不执行真实业务。

目录路径中的应用及模块 id 都由后端验证；不可利用另一系统模块 id 读取其功能。用户可进入应用，并不代表拥有该应用的全部操作。

==== 人员列表

`GET /users/page?q=&company=&departmentId=&page=0&size=20`。

* q 匹配姓名、登录名、电话、工号；company 是公司名称；departmentId 是部门 id。
* 筛选条件只能缩小授权范围，不能扩大范围；越界筛选返回空列表及 total=0。
* page 小于 0 时取 0；size 小于 1 时取 1，大于 100 时取 100；`/users` 默认 size=30。
* 每项含 id、employeeNo、username、name、phone、company、departmentId、department、position、status、employmentStatus、roles、managementActions。
* managementActions 给出目标可尝试的 user.roles／handover.start／handover.complete。角色权限子集、离职状态等业务前置条件仍在写入时检查。
* 无部门人员只有 GLOBAL user.read 可以查看；分页 total 与 items 使用相同范围谓词。

==== 业务角色与权限替换

请求体统一为 `{"ids":[1,2]}`；null 列表为 400；空数组表示撤销全部。去重处理，不存在的角色／权限 id 不建立关联；界面应仅提交服务器返回选项。所有授权替换均写 authorization_changes。角色权限写入的目标角色 ID 必须来自角色目录；非法目标在实际建立关联时由外键约束拒绝，不约定所有目标错误都返回 404。

角色替换采用增量更新：保留角色的范围不变；撤销角色级联删除其范围；新角色不会自动获得管理范围。范围由 role-assignments 专用接口调整。禁止已完成离职的人员重新分配角色；局部管理员对子集校验不通过的目标不能部分修改。

==== 角色管理操作权限

`PUT /roles/{id}/management-permissions` 请求 `{"permissions":["user.read","user.roles","org.read"]}`。空数组撤销此角色的管理操作，影响所有角色持有者；员工范围保持不变。未知权限或无效角色返回 400。
`audit.read`、`role.permissions`、`management.grant` 仅允许配置给系统管理员角色，运行时还必须有 GLOBAL 范围。配置后必须保留至少一名有效平台授权管理员。

==== 员工角色与范围

`GET /users/{id}/role-assignments` 返回：roles 中包含 id、code、name、enabled、assigned、managementPermissionCount；scopes 每项包含 roleId、scope、companyId、departmentId。

[source,json]
----
{
  "roleIds": [3, 5],
  "scopes": [
    {"roleId":3,"scope":"COMPANY","companyId":10,"departmentId":null},
    {"roleId":3,"scope":"DEPARTMENT","companyId":11,"departmentId":20}
  ]
}
----

示例 id 仅说明结构，应使用接口返回的真实选项。两数组必填，范围最多 200 条；范围必须绑定 roleIds 中的启用角色。公司／部门必须启用且归属正确，空值／多余组织字段必须符合范围表。相同范围去重，目标必须 ACTIVE。
保存会原子替换角色与范围并写 SET_ROLE_ASSIGNMENTS；空数组可撤销全部，但不能撤销最后平台授权管理员。任何失败整体回滚。仅设置角色并不会自动授予管理范围。

例如某人持有角色 A 的人员查询权限并绑定甲公司、角色 B 的人员修改权限并绑定乙公司，不能用 B 的修改权操作甲公司人员。
`/me.managementGrants` 字段仅作为派生有效权限供前端消费。

==== 组织维护

新增公司（POST）：`{"code":"COMPANY_A","name":"A 公司"}`。
新增部门：`{"code":"DEPT_A","name":"工程部","companyId":10}`。
修改公司／部门（PATCH）允许 `{"code":"DEPT_A","name":"新名称"}` 或只提交其中一项，不得提交 companyId 或 parentId。编码 1–100 字符，名称 1–191 字符，不允许空白值。

组织只包含公司及其部门，不设部门层级。组织维护不提供删除、移动或停用接口。拥有 org.write 的部门范围管理员可改名其已有部门，但不能新增部门；公司／平台管理员可在有权公司新增部门。parentId 非空属于无效输入；授权计算始终按精确部门。部门负责人字段不在此维护接口中调整。

==== 离职与审计

发起：`{"receiverNo":"工号","ownerNo":"工号","expectedDate":"2026-11-01","reason":"交接说明","oaReference":"可选单号"}`。

接收人和负责人必须启用、未进入交接且不是离职本人，同时在 handover.start 的授权范围内。不能为当前登录账号办理离职。日期为 YYYY-MM-DD；reason 最长 1000，OA 单号最长 200。开始交接保留授权，不给接收人自动复制角色。

完成：`{"note":"完成说明","confirmed":"true"}`。note 最长 1000。事务内删除用户角色并级联删除角色范围、停用用户、撤销会话、更新交接状态并记录变更；已完成交接重复请求直接返回成功，权限仍需校验。

交接详情中的接收人／负责人如果已不在查看者 user.read 范围内，返回“范围外人员”，工号与 id 为 null。管理授权配置明细仅对 GLOBAL management.grant 查看者开放，其他人员的交接历史过滤该变更类型。

鉴权日志仅系统管理员在 GLOBAL audit.read 生效时可读，返回全部范围日志，包括无法关联当前用户的历史记录。公司领导、部门经理、项目经理不能查看该全局日志。

=== 日志查询与归档

GET `/authorization-logs` 的可选参数：


[cols="1,1",options="header"]
|===
|参数 |类型与语义
|userId |正整数，精确匹配内部用户 ID；未识别身份的记录为空 ID
|username |最长 100 字符，精确匹配记录中的账号快照；登录事件保留尝试的登录标识
|appCode |最长 191 字符，精确匹配系统编码；认证事件为空系统码
|allowed |true 或 false；成功／允许与失败／拒绝
|from / to |UTC ISO-8601，含 from、不含 to；from 必须早于 to
|event |最长 32 字符；AUTHORIZATION、APPLICATION_ENTRY、LOGIN_SUCCESS、LOGIN_FAILED、UNAUTHENTICATED、REQUEST_DENIED
|storage |ALL（默认）、ACTIVE、ARCHIVED
|limit |1–500，默认 100
|cursor |后端返回的不透明游标；继续查询须保持所有筛选条件及 limit 不变
|===


[source,json]
----
{"code":"OK","message":"成功","data":{"items":[],"nextCursor":null,"hasMore":false,"snapshotId":0},"requestId":"服务端生成的 UUID"}
----

items 每项包含 id、occurredAt、userId、username、appCode、permissionCode、allowed、requestId、reason、eventType、httpMethod、requestPath、httpStatus、archivedAt、archivedBy。
时间按 UTC 解释；归档字段为空表示未归档。按 id 倒序，首次记录最大 id 作为查询上界，后续按小于上一页末 id 查询，避免新日志插入导致重复；新记录在重新查询时出现。
这不是数据库事务快照：若同时归档，ACTIVE/ARCHIVED 集合会变化，应重新查询；ALL 的事件集合保持可追溯。不提供按页码跳转。

POST `/authorization-logs/archive` 请求 `{"before":"2026-10-01T00:00:00Z","batchSize":1000}`。
截止时间必填且不能晚于当前时间；batchSize 1–5000，默认 1000。仅归档 occurred_at < before 且尚未归档的记录；一次固定最大 id 后按 id 升序更新至批量上限。
返回 `{"archived":1000,"hasMore":true,"snapshotId":12345}`，hasMore=true 时可用同一条件继续。每批事务写 archived_at/archived_by 和 ARCHIVE_LOGS 变更审计；重复请求不会重复归档已完成记录。
此操作针对截止时间前的全部记录，不受列表筛选影响。逻辑归档不删除、不搬离数据库、不减少表占用空间；本设计不提供自动清理或外部冷存储。

认证审计在请求结束时记录登录成功、登录失败及 API 的 401/403；未提供令牌、过期、撤销、停用账号均留痕。无法识别身份时 userId 为空；JSON 无法解析时账号也可为空。
不得记录密码、令牌、请求体或查询字符串。业务鉴权和应用准入记录操作结果；拒绝的应用准入还可能产生一条 REQUEST_DENIED 请求记录，通过请求标识关联。
不存在的系统返回 404，属于资源错误，不伪装成鉴权判定。日志写入使用独立事务，使业务回滚不撤销认证失败留痕；数据库本身不可用时不能保证持久化成功。

=== 统一响应与业务错误码

局部管理员访问范围外或不存在的人员统一拒绝，避免用返回差异探测。GLOBAL 查询角色分配时，即使目标不存在也返回角色选项和空范围；写入必须校验目标状态。

权限在每次请求中读取；撤权提交后新查询立即生效。Vue 定时和窗口聚焦刷新 `/me`，管理授权集合变化时卸载旧视图、重取范围内数据；无当前页面权限时回到我的应用。已经通过鉴权的外部在途业务操作不保证被中断。

授权编辑不设置版本冲突提示；多个合法管理员顺序保存采用最后一次提交。所有管理写入串行化是小规模管理系统的串行一致性选择；规模扩展须评估锁粒度与竞争。

==== PUT 与 PATCH 的字段语义

角色、权限和角色范围使用 PUT 完整替换集合。公司、部门使用 PATCH 局部更新，Content-Type 为 application/json。

例如 `PATCH /organizations/departments/12` 的请求 `{"name":"工程部"}` 只修改名称，编码、所属公司与负责人不变；`{"code":"DEPT_12"}` 只修改编码。
code/name 至少提供一个；省略表示保留，显式 null、空白、code 超过 100 字符、name 超过 191 字符，以及 companyId/parentId/enabled 等其他字段均返回 HTTP 400、code=INVALID_ORGANIZATION_PATCH。重复同一合法 PATCH 保持相同资源状态。成功响应 data=null；组织资源不接受 PUT，返回 HTTP 405。

== 响应模型与字段字典

== 关键交互与状态设计

=== 登录与带令牌访问


[cols="1,3,5",options="header"]
|===
|顺序 |责任组件 |动作／失败分支
|1 |RequestAuditFilter |生成服务端请求号，建立请求审计上下文。
|2 |ApplicationService / AuthService |校验长度，规范化登录账号，通过唯一标识登记查询用户；账号停用、未知或密码不匹配统一 LOGIN_FAILED。
|3 |AuthService / AuthRepository |生成随机令牌，将摘要与到期时间写入 sessions；登录事务提交后返回令牌。
|4 |RequestAuditFilter / AuditRecorder |请求结束时记录 LOGIN_SUCCESS 或 LOGIN_FAILED；不记录密码或令牌。
|5 |后续业务 Service |解析 Bearer，查询摘要、撤销标志、到期时间、账号状态，再按本次资源校验权限。
|6 |ApiResponseAdvice / ApiExceptionHandler |返回统一响应；401 促使前端清理身份，403 促使前端刷新权限。
|===

=== 管理写事务顺序

[source,text]
----
开始事务 → 锁系统管理员角色行 → 按当前授权核验操作与范围
         → 校验全部输入与目标保护 → 按需锁目标人员／交接
         → 执行业务更新 → 检查最后平台管理员 → 写变更审计 → 提交
任何业务异常／SQL 异常 → 整体回滚 → 返回错误码
----

部分业务可在锁前验证会话，但管理操作与范围必须在取得公共锁后判断。公共锁只协调遵守该协议的应用写事务；直接 SQL 写入不受应用授权算法保护。读接口不持有该公共锁。


[cols="2,4,4",options="header"]
|===
|操作 |事务内必须同时完成 |失败后不变量
|角色分配 |增量修改 user_roles、级联范围、最后管理员检查、SET_ROLES |保留原角色及其范围。
|角色范围保存 |校验角色与范围、修改角色、重建范围、最后管理员检查、SET_ROLE_ASSIGNMENTS |不能只保存角色而丢失范围，或相反。
|角色管理权限 |替换 role_management_permissions、平台专属操作校验、最后管理员检查、审计 |不能使最后一名授权管理员失去管理授权能力。
|组织 PATCH |授权校验、code/name 局部修改、变更审计 |唯一性冲突时原编码／名称保留。
|离职完成 |删除角色、级联范围、停用用户、撤会话、完成记录、审计 |不能只停用一部分授权或先标记完成。
|日志归档 |固定 ID 上界、批量归档元数据、ARCHIVE_LOGS |批次原子提交；不同批次之间不共享数据库事务快照。
|===

=== 离职状态转换


[cols="2,4,2,4",options="header"]
|===
|起始状态 |事件／前置条件 |目标状态 |权限与数据影响
|EMPLOYED（无记录） |发起；本人、接收人、负责人及范围校验通过 |HANDOVER |创建交接记录；保留本人权限，不自动授予接收人。
|HANDOVER |明确确认完成，完成权限与最后管理员保护通过 |DEPARTED |账号 DISABLED，角色及范围撤销，会话撤销。
|HANDOVER |再次发起 |保持 HANDOVER |HANDOVER_EXISTS，无重复记录。
|DEPARTED |再次完成且操作者仍有权限 |保持 DEPARTED |成功返回，不重复执行业务撤权。
|任意状态 |非法输入、无权或范围越界 |保持原状态 |返回对应错误；不产生半完成业务状态。
|===

系统不定义交接取消、回退或复职接口。账号 ACTIVE／DISABLED 与交接状态属于不同维度，不能仅由一个字段推导另一字段。

=== 审计游标与归档算法

首次查询读取最大日志 ID S，组合过滤条件，按 id DESC 查询 limit+1 条。后页解码 S、上页末 ID B 及条件指纹，使用 id≤S 且 id<B；返回超出 limit 的一条只用于判断 hasMore。
游标绑定筛选条件和 limit，不绑定身份，也不是签名授权凭据；每次仍需重新认证和权限判断。客户端不能修改游标或依赖其编码结构。
S 仅排除后续分配更大 ID 的事件，不提供跨页事务快照；归档状态变化、并发事务提交顺序都会影响可见集合。需要重新读取最新数据时必须从首屏重新查询。
归档每批读取自己的 S，更新 occurred_at<before、未归档且 id≤S 的最早一批记录。hasMore 表示该上界内仍有匹配项，多批调用可能得到不同 snapshotId。归档不受当前列表的用户或系统筛选限制。


== 安全、容量与异常设计

* 身份与授权：令牌使用安全随机数；数据库仅存摘要；不把权限缓存到令牌。组织筛选附加于授权谓词，不替代授权谓词。
* 输入与 SQL：动态排序和表名不得直接来自客户端；筛选值采用参数绑定。PATCH 白名单限制字段；登录错误不区分账号未知、停用或密码错误。
* 并发与重试：角色公共锁串行化管理写事务。数据库死锁或瞬时故障不约定自动重试；客户端必须先检查响应及资源状态，不能盲目重放创建或交接发起请求。
* 审计边界：认证失败事件独立事务保存，管理变更与业务写事务同时提交；独立审计不等于消息队列或持久化补偿，数据库不可用时不承诺必达。
* 数据暴露：禁止返回密码摘要、会话摘要或 SQL 堆栈；人员联系方式按管理范围可见；交接关联人范围外标识遮蔽。日志的主体可能为空。
* 会话与前端：会话令牌保存在浏览器 sessionStorage；会话过期后重新登录。该选择不能消除 XSS 风险，界面不得把非可信文本当 HTML 执行。
* 容量控制：人员页最多 100 条、日志页最多 500 条、归档批次最多 5000 条、人员范围最多 200 条；共享角色和目录接口不提供分页，适用于受控目录规模。
* 性能评审：公共锁吞吐、范围 EXISTS 查询、LIKE 前置通配符与日志组合筛选必须纳入容量评估；不以存在索引推导固定响应时延，不在设计中虚设 QPS 或 SLA 数值。
* 功能边界：本设计不提供令牌刷新、MFA、登录限流／锁定、审计防篡改签名、自动日志清理、分布式缓存或外部业务事务中断协议。扩展这些能力需独立定义接口和一致性规则。

== 设计验证与需求追踪

验证以预期行为为判据，不以执行覆盖率代替正确性。单元验证负责规则与故障分支，独立 MySQL 集成验证负责 SQL、触发器和事务，接口验证负责 HTTP 契约，界面验证负责交互与权限变化反馈。


[cols="1,3,6",options="header"]
|===
|设计标识 |设计目标 |验证场景与预期结果
|AUTH-01 |统一登录与会话撤销 |三种标识定位同一用户；账号停用、到期或撤销后拒绝请求；响应不包含摘要。
|RBAC-01 |有效业务权限并集 |多角色去重；目录任一节点停用后相应权限失效；应用准入不等于全部操作许可。
|SCOPE-01 |同角色操作与范围关联 |角色 A 的查询权不得与角色 B 的范围组合为修改权；跨公司／精确部门访问受限。
|ADMIN-01 |保留平台授权能力 |撤销最后 GLOBAL management.grant 或最后管理员离职时业务事务回滚。
|ORG-01 |PATCH 局部更新 |只改名称保留编码；非法字段、null、空白、超长和重复编码被拒绝；PUT 组织路径返回 405。
|INIT-01 |空库初始化一致性 |约束先建立，数据与默认授权同一事务导入；失败无部分业务数据；非空库重启不恢复撤权。
|LEAVE-01 |离职原子处置 |完成后角色、范围、账号、会话和状态一致；失败全部回滚；重复完成不重复处置。
|AUDIT-01 |审计查询与归档 |筛选条件准确，游标条件变更拒绝，UTC 半开区间有效，批次归档不删除事件。
|API-01 |统一响应 |成功及错误均有 code/message/data/requestId，HTTP 状态正确，内部异常不泄漏 SQL。
|UI-01 |界面反馈 |授权变化卸载旧视图并重新查询；403 不显示操作成功，分页与编辑草稿状态一致。
|===

# 市政公司统一权限管理系统——需求分析

版本：1.0；日期：2026-10-08；阶段：RBAC0 课程项目；技术约束：Spring Boot + Vue + MySQL。

## 1. 编写目的与依据

本文定义本阶段业务目标、系统边界、功能、规则和验收口径，供界面、接口、数据库及详细设计引用。依据为三份业务 Excel、已收集的需求、用户后续明确要求及当前项目代码。

三份数据源为员工信息表、部门信息表、应用软件功能权限清单。初始化基线为 10,000 名员工、1 个初始化管理员、111 个部门、18 个系统目录、5 个角色、2,521 个操作权限；这是当前资料的导入结果，不是系统容量上限。录音背景中的“20 余系统”与当前资料列出的 18 个系统不矛盾。

用户后续明确将系统选择页、离职交接、公司/部门筛选、电话显示及前后端分离纳入课程演示。老师补充数据库必须使用 MySQL，项目已由 SQLite 迁移至 MySQL 8.4，并保留旧库作为迁移来源与备份。

## 2. 业务背景与目标

集团员工跨部门使用多个业务系统，分散的账号和授权难以统一掌握。员工调岗或离职时，逐系统处理容易遗漏；仅隐藏菜单不能阻止直接调用后端接口。

本阶段目标：

1. 统一维护身份、角色、功能权限及两组授权关系。
2. 用工号、手机号或用户名登录，区分“认证成功”“获准进入系统”“获准执行操作”。
3. 通过后端逐次查询实现撤权提交后的新鉴权立即按新权限判断。
4. 集中办理离职交接，保留历史人员与审计记录。
5. 提供可演示、可维护、前后端分离的管理界面和接口。

## 3. 参与者与边界

| 参与者 | 权责 | 当前实现 |
|---|---|---|
| 普通员工 | 登录、查看自己的系统授权、请求准入 | 已实现；不能访问管理列表或修改授权 |
| 系统管理员 | 全局查询用户、分配角色、配置角色权限、办理交接、查看日志 | 持有启用的“系统管理员”角色即可；尚未按管理操作细分 |
| 交接接收人 | 接收业务资料与工作 | 平台记录其工号，不自动继承离职者权限 |
| 交接负责人 | 负责确认交接情况 | 作为记录关联人员，提交操作仍由管理员执行 |
| 业务系统后端 | 受控操作前调用鉴权接口，执行自身业务 | 已有接口；18 个系统尚未实际接入 |
| HR/组织数据提供方 | 提供人员及部门资料 | 已实现首次 Excel 导入，未实现持续同步 |
| OA | 申请、审批与交接流程 | 仅记录 OA 单号，未实现审批引擎或可信回调 |

“公司领导、部门经理、项目经理”属于业务角色，不天然拥有权限平台管理权。组织上下级不产生角色继承。

本阶段不实现：RBAC1 角色继承、RBAC2 互斥约束、行级/道路级数据权限、完整用户增删改、角色和系统目录 CRUD、部门分级管理员、密码重置、再入职、撤销交接、跨系统单点登录、通用报表和真实业务系统。

当前“我的应用”是后续明确要求的演示性系统选择页，不代表建设集团完整导航门户；这与原始访谈排除通用门户的边界需要在答辩时说明。

## 4. RBAC0 业务规则

设 U 为用户集合，R 为角色集合，P 为权限集合；UA 为用户—角色关系，PA 为角色—权限关系。一个用户可持有多个角色，一个角色可包含多个系统的权限。

- 用户不直接绑定权限，只经由角色获得权限。
- 所有已分配且启用的角色均参与当前会话鉴权，不提供逐会话选择激活角色。
- 有效权限取所有有效角色权限的去重并集；未命中即拒绝。
- 角色、权限、所属系统必须启用；账号必须启用且会话有效。
- 移除一个角色后，另一角色授予的相同权限仍然有效。
- 系统准入条件为该系统存在至少一个当前有效权限；不等于可执行其中全部功能。
- 管理后台准入单独判断有效角色 code 为“系统管理员”，不由岗位名称或系统卡片状态推断。
- 授权变更以数据库事务提交为边界。已在撤权前通过鉴权的外部业务长事务不在当前中断保证范围内。

### 5.1 查询与展示细则

公司与部门采用精确匹配，关键词在姓名、用户名、工号、手机号中模糊匹配；关键词内部为 OR，与组织条件之间为 AND。切换公司清空部门并重置页码；部门选项仅列出该公司当前有人员关联的部门。未选择公司时可选择全部人员关联部门。每页界面固定 20 人，空电话显示“—”，不将手机号转换为数值。

### 5.2 离职交接细则

账号状态 ACTIVE/DISABLED 与人员状态在职/交接中/已离职分离。没有 handovers 记录视为在职。

1. 发起对象必须存在、账号启用、无既有交接记录，且不能是当前操作者。
2. 接收人与负责人按工号查找，必须启用且没有交接记录，均不能是离职者；当前允许接收人与负责人为同一人。
3. 必填接收人工号、负责人工号、预计完成日期、交接说明；OA 单号可选。当前不强制预计日期晚于今天。
4. 交接中不自动撤权、不过户权限、不因预计日期到期自动完成；必要时管理员手动调整角色。
5. 完成必须填写说明并明确确认；在同一事务内删除全部用户角色、禁用账号、撤销所有会话、更新交接状态和记录原角色。
6. 重复完成返回成功而不重复记账；已离职者禁止重新分配角色。保留用户，不物理删除。

### 5.3 日志范围

已通过身份认证的功能鉴权和有效目标系统准入，允许与拒绝均记录。未登录请求、登录失败和不存在的系统准入目前不保证记录在鉴权日志中。日志反映“鉴权结果”，不表示业务操作执行成功。角色修改记录权限数量，用户角色修改记录角色 ID 集合；并非所有变更都保存完整前后差异。

## 6. 主要用例

| 用例 | 参与者与前置条件 | 主流程 | 异常或后置条件 |
|---|---|---|---|
| UC-01 统一登录 | 员工；账号已导入 | 输入凭据→校验密码和状态→签发会话→系统选择页 | 错误统一提示；停用无法登录 |
| UC-02 查找员工 | 管理员已登录 | 选择公司→选择部门→输入关键词→查询/翻页 | 空集显示明确提示；不泄露给普通员工 |
| UC-03 用户授权 | 管理员、目标存在且未离职 | 打开角色弹窗→调整勾选→保存→刷新列表 | 权限回收时接口拒绝；空集合代表撤回全部 |
| UC-04 角色配置 | 管理员 | 加载全部选项→筛选→勾选→保存完整集合 | 其他隐藏选项不得被误清空 |
| UC-05 动态访问 | 已登录员工 | 查看卡片→点击入口→服务端重查→显示结果 | 授权被回收返回拒绝；有权但未接入提示未接入 |
| UC-06 离职处置 | 管理员、目标启用 | 发起交接→线下/OA完成→填写说明确认→集中撤权 | 非法人员、重复发起、自办离职拒绝；完成原子提交 |
| UC-07 功能鉴权 | 业务调用方携带用户令牌 | 传 appCode、permissionCode→验证有效关系→记录结果 | 不匹配返回 allowed=false；服务不可用不应放行 |

## 7. 非功能需求与实现程度

| 类别 | 要求 | 实现或验收边界 |
|---|---|---|
| 安全 | 密码不可明文存储；后端鉴权不能被前端绕过 | BCrypt；数据库只存令牌 SHA-256；API 逐次校验 |
| 隐私 | 员工姓名电话限制访问 | 管理接口限制访问，当前授权管理员可见明文；字段加密/脱敏待实现 |
| 一致性 | 多表离职处置全成或全败 | MySQL InnoDB 事务与目标用户/交接行锁 |
| 实时性 | 撤权提交后的新鉴权读取最新状态 | 不使用权限结果缓存；前端 3 秒轮询只服务展示 |
| 可用性 | 故障不静默绕过权限 | 前端提示网络失败；未实现集群、高可用与灾备 |
| 性能 | 支撑一万量级人员查询及高峰使用 | 有分页、索引、连接池；未完成并发压测，不声称达到 20ms |
| 留存 | 原始业务要求日志永久保存 | 当前无自动清理，尚未建设长期归档、容量治理和恢复机制 |
| 可维护性 | 五份设计文档与源码一致 | 分离前端、API、认证、初始化、DDL；数据库连接外部配置 |
| 兼容性 | 现代浏览器、UTF-8 中文数据、响应式 | 桌面表格，窄屏内部横向滚动；具体浏览器兼容矩阵待补测 |

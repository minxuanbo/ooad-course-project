## 第二轮用户反馈与处理范围

| 用户反馈/确认 | 原型设计 |
| --- | --- |
| 只有人员操作，缺部门维护 | 独立部门管理；用户确认仅系统管理员、首版只改名称，不扩展新增/删除/层级调整 |
| 人员需要当前角色和职位 | 两列独立展示，含停用角色；用户确认职位只读，人事系统负责职位维护，本RBAC不增加职位编辑/职位调动 |
| 管理员界面缺角色权限、鉴权日志等 | 补齐角色查询/新建/改名/启停/独立选权，资源树/API启停/完整映射，日志筛选/快照/详情 |
| 新增总览，公司概况由我们设计 | 同一入口按范围统计人员状态和组织分布，获准快捷入口；全局日志不能混入部门概况 |
| 项目经理不应授予公司领导 | 用户明确批准五级授予矩阵；候选与保存同时验证级别、完整Permission子集、部门范围；自定义角色默认仅管理员可授 |

具体交互、演示账号、文件及运行方法见[原型说明](../prototype/v2/README.md)。

## 新需求与当前代码的边界

本轮确认已进入[需求R23—R26](requirements.md)，原型据此实现。正式后端、frontend、OpenAPI、SQL及原Excel均未变。当前正式API不返回人员职位/角色摘要，也没有本轮部门改名或总览聚合契约；正式角色尚无本轮新增级别约束。不能把新原型称为现有后端已支持。

原型满意后，需先补齐并审核上述接口、角色元数据及维护恢复约束、部门目录/改名与原导入映射兼容方案，再开展正式实现。角色级别不作为API授权替代，职位不作为运行时权限来源。历史T13和阶段2验收不因新规则自动失效或变成新规则验收证据，须按后续版本补回归。

## 验证与限制

第二轮当前Node检查覆盖原行为和级别矩阵、角色完整Permission子集、自定义默认策略、部门改名不改变归属、只读职位、权限独立选择、关键API/映射/角色的回滚、日志脱敏及同快照分页。浏览器另检查实际显示和点击流程；结果在最终审核后追加。

全部168人员、15组织及示例岗位均虚构。响应延迟、鉴权事件、requestId及原型回滚只是内存演示；不代替真实HTTP、JPA事务、并发锁、万人性能或两套后端验收。无用户最终批准，不合并、不改正式前端、不启动DDD/T14/T15或部署。

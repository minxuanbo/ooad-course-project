# RBAC 检查记录复核说明

以《2-9组检查记录》第一轮技术纪要为基础，结合补充检查图片和用户确认复核。原纪要摘录保持原文，图片、数据与用户补充分节注明来源。本文保留技术内容；原 DOCX 及人员、评分信息留在本地。

## 1. 检查纪要技术摘录

源纪要说明：录音文件为 2-9.m4a（约25分13秒），正文是依据录音整理的结构化纪要，不是录音逐字稿；第二、三轮尚无检查记录。以下逐段保留技术正文，作为小组核对依据。

### 一、ER图与需求

ER图应使用标准符号并只表达核心对象。User、Role、Permission及两组多对多关系必须保留，日志、登录凭证、业务功能点、OA模块等非本轮核心内容不应进入ER图。

公司可并入层级Department；部门扩展用于一万多名用户的分部门管理。管理员由角色中的管理权限决定，并以同部门/下级部门范围限制授权对象，不需要管理员属性。

权限应具体化为菜单和按钮树；API需单独建模并与菜单/按钮建立关系，以便从用户角色推算可调用API。下一阶段需覆盖本权限系统和课程管理系统两个系统。

统一登录标识、离职交接、会话、角色版本和复杂业务模块不属于本轮权限系统核心需求，应删除。当前阶段采用令牌登录，会话不写入数据库。

### 二、API设计

当前API直接由需求文档生成，结果混乱且缺少分页、部门分组、搜索等场景。应先做出正确的界面原型，再由界面生成API并逐项审核。

人员列表面对一万多名用户，必须按部门显示并支持搜索、分页；只返回全部用户的接口不可接受。API说明应由需求文档补充并作为后续代码生成契约。

### 三、代码与架构

后端代码缺少模块和分层控制，生成时未审查可读性，并使用JDBC直接写SQL。应明确Controller、Service、Repository结构、模块边界及技术栈。

下一轮必须使用课程规定技术，特别是Spring Data JPA和AOP；AI默认倾向旧技术，需持续检查和校正输出。

### 五、整改重点

重画核心ER图；删除会话、凭证、功能点、离职交接等超范围内容；补部门和多系统；建立菜单/按钮—API关系；重做分页、搜索和部门分组接口；按JPA和AOP重构代码。

### 1.3 登录要求与字段口径

## 3. 方案建议与用户补充

方案默认包括角色全局共享、单部门归属、共同根人员维护全局资源、权限与 API 多对多、九张表、分页默认 20/最多 100、整体替换和停用替代删除。这些是实现建议，课程尚未正式指定 RBAC0；老师明确要求另按第 1 节与对照表记录。

保留防越权、事务回滚及最后有效管理员保护，审批、交接和日志平台留在范围之外。实际权限决定可执行操作，根部门位置限定全局范围；部门管理员管理本部门及下级，本轮组织功能为部门树查询，完整组织 CRUD 留在范围之外。

**2026-11-07 最新用户确认，覆盖此前约定：**

- 普通员工及无本系统有效管理权限账号拒绝登录：沿原账号/口令流程复用有效权限查询增加准入判断，仍逐请求校验具体权限及部门范围。岗位/角色名不作为准入依据，管理员字段、资格表、额外认证接口和令牌机制不新增。
- 复用最小鉴权日志并迁 JPA：有日志查询权限的全局维护者可查看，部门管理员拒绝。保留最小记录和查询，归档、导出、变更历史及完整审计移除，日志留在核心 ER 之外。

上述补充由下游实现与验收；T01/T02 保留 2026-11-02 的历史评审证据。

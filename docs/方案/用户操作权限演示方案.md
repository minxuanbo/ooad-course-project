# 用户操作权限演示方案（待实施）

## 为什么目前无法演示

当前管理接口统一检查有效“系统管理员”角色，普通员工只有应用选择页。功能清单中的操作权限虽然已入库，但用户增删改查接口尚未全部实现，也没有逐项绑定权限。现在能演示系统准入和撤权，不能据此声称完成操作级权限演示。

## 接入范围

将本项目管理页面作为“系统管理后台”的真实入口，保留“我的应用”。后台页面准入与具体操作分开：获授至少一个后台功能权限可进入；具体功能分别检查。这里的准入规则延续现有规则，不引入角色继承。

先实现用户模块的小闭环：列表与详情查询、新增用户、编辑基本信息、归档用户。历史员工不物理删除。停用账号、角色授权和离职处置必须是单独权限，编辑基本信息不能顺便修改这些字段。

## 权限与接口

下面的编码是拟定的稳定编码。实施前逐项映射既有清单，保留已有角色授权，避免重复创建同义权限。

| 权限 | 拟定接口 | 作用 |
| --- | --- | --- |
| iam:user:read | GET /api/users、GET /api/users/{id} | 查询用户 |
| iam:user:create | POST /api/users | 创建账号，默认无业务角色 |
| iam:user:update | PATCH /api/users/{id} | 修改姓名、联系方式、任职 |
| iam:user:archive | POST /api/users/{id}/archive | 归档停用且已撤权的账号，保留历史记录 |
| iam:user:disable | POST /api/users/{id}/disable | 紧急停用并撤销会话 |
| iam:user:assign-role | PUT /api/users/{id}/roles | 调整角色，独立于 CRUD |
| iam:handover:read | GET /api/users/{id}/handover | 查看交接及授权概况 |
| iam:handover:start | POST /api/users/{id}/handover | 开始离职交接 |
| iam:handover:complete | POST /api/users/{id}/handover/complete | 集中撤权、停用与撤销会话 |

“删除”演示为业务删除（归档），界面按钮应明确标注“归档”，不能伪装成物理删除。归档权限不隐含离职处置权限；未满足停用和撤权条件的目标拒绝归档。

## 角色与测试账号

- 用户查询员：仅授予 read，可以查看列表与详情，其他操作不可用。
- 用户维护员：授予 read、create、update、archive，展示增删改查；不授予角色授权、账号停用或离职处置权限。
- 离职办理员：授予 read、handover:read、handover:start、handover:complete。
- 初始化管理员：通过角色显式获授所有管理权限。逐步替换现有角色名称硬编码判断。

使用三个独立测试账号。一个账号只分配其演示所需角色，避免其他角色通过权限并集继续授予被撤销的权限。角色没有继承，允许组合。

## 前后端执行

1. 登录后获取当前权限，按功能显示菜单、按钮。对只读用户显示“只读：仅可查询”。
2. 每个后端操作检查自己的稳定权限编码，未授权返回 403 并记鉴权日志。
3. 页面每 3 秒更新状态，重新聚焦时刷新；保存表单时始终后端重新鉴权，拒绝后保留输入并提示。
4. 权限写操作的校验与业务写入采用一致的事务边界，避免鉴权后再执行时的竞态。明确撤权提交后新发起的请求一定拒绝；跨应用在途事务需单独约定。
5. 新增/修改做字段白名单及工号、用户名、手机号冲突检查，不能通过附加 roleIds 或 status 绕过独立权限。
6. 授权日志记录允许/拒绝；业务变更日志记录具体目标和前后值，密码不入日志。

## 演示顺序与验收

1. 查询员登录：只能查询，构造新增/修改/归档请求也返回 403。
2. 维护员登录：创建测试账号，修改信息；对满足条件的测试记录归档。
3. 维护员打开编辑表单，管理员撤销 update：无需重新登录，提交立即拒绝，数据库内容不变。
4. 恢复 update：再次提交成功。
5. 撤销角色 A，但角色 B 仍授予 update：继续允许；从所有角色回收后才拒绝。
6. 离职交接开始时原会话仍可用；完成后所有旧会话失效，登录拒绝，历史记录保留。

本文件是方案，除现已完成的离职交接功能外，不代表上述 CRUD 接口和逐项权限已落地。

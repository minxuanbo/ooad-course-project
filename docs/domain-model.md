# 领域模型与业务规则

版本：1.1评审稿。本文先表达业务概念，再提出DDD边界；当前代码仍是结构化Service与JPA实体，本文不声明DDD已落地。需求依据为[需求说明](requirements.md)，既有Chen ER见[数据库设计](database-design.md)。

## 1. 统一业务模型

| 业务概念 | 责任、行为与不变量 |
| --- | --- |
| 用户User | 单一内部身份、一个所属部门、零到多个角色；分配角色、停用、调动保持同一id。工号/手机号定位同一账号，不按姓名唯一定位。 |
| 角色Role | 全局共享的权限集合；可改名/启停/整体替换权限，编码稳定。停用不删除关联，恢复后按当前资源状态重算。 |
| 权限Permission | 同一系统的菜单或按钮；维护父级、类型、有效状态及显式API映射。父菜单负责展示，不隐含子权限。 |
| API资源ApiResource | 单一系统的方法+路径模板，表达后端操作入口。多个权限可覆盖同一API，以有效链OR判定。 |
| 应用系统ApplicationSystem | 权限与API的归属和有效性边界；当前管理目录为rbac，外系统目录不能进入本轮维护。 |
| 部门Department | 公司/分公司/部门的层级节点；定义人员归属与子树范围，不直接给人授予权限。 |

“全局管理员”是某个User在当前授权与组织状态下满足完整K的业务谓词，不是实体、字段或固定角色名称。首次admin只是初始化来源；其他用户可通过合法授权形成相同能力，失效后也不再满足该谓词。

## 2. 核心业务判定

有效API集合由用户所持启用角色的启用权限映射得到，且用户、API及其同一所属系统均启用。具体操作先检查该API，再检查人员范围或共同根范围。人员角色候选以有效Permission ID全集作子集比较，不能仅比较API路径，也不能丢弃外系统部分后继续授予。

人员归属决定可管理子树：总公司领导归根后覆盖所有分公司，分公司领导仅覆盖该分公司及后代。组织位置只约束范围；领导/经理称谓不授予操作权限。

全局维护保护是跨对象不变量：相关写提交后至少存在一个启用根用户，独自覆盖完整17项K。角色、权限、映射、API、人员角色、人员状态和调动都可能影响此结论，因此不能把检查局限在单个Role实体内。

## 3. DDD拟议聚合与依赖

以下为目标设计，后续实施前按真实写场景复核；不为每张数据库表机械生成一个领域服务。

| 拟议聚合/对象 | 边界与标识引用 |
| --- | --- |
| User聚合 | 用户资料、状态、departmentId与显式roleIds；通过领域行为变更，不把Role或Department的可编辑JPA对象直接嵌入。 |
| Role聚合 | 稳定编码、名称、状态、显式permissionIds；Role不管理所有用户，也不持有整个授权图。 |
| Permission聚合 | 系统标识、父标识、类型、状态和显式apiIds；跨节点无环、同系统及按钮子节点约束由领域规则结合仓储事实检查。 |
| ApiResource聚合 | 系统标识、稳定方法/模板、启用状态；状态变更须参与全局维护保护。 |
| Department与ApplicationSystem | 保持稳定标识及业务约束；当前只读场景可采用读取模型，不为未要求的组织/系统CRUD增加命令。 |
| 值对象 | 候选包括部门范围、方法/路径组合、有效权限集合、角色分配集合；只有封装实际规则时才引入，不包装所有字符串和ID。 |
| 领域策略 | 有效授权计算、角色可授予判断、人员变更限制与完整维护能力判断；输入业务事实，输出业务结论，不依赖HTTP/JPA。 |

同一根锁下的业务事务由应用服务编排：读取锁后最新事实→调用领域规则/行为→通过仓储端口持久化→检查完整K→提交。跨聚合保护使用同一事务与稳定锁点，不引入消息最终一致性、分布式事务或把全数据库装成一个巨大聚合。

DDD仓储接口位于领域/用例端口，Infrastructure实现JPA适配与装配；应用服务不得引用EntityManager、JpaRepository或JPA Entity。结构化与DDD可以共享错误码、用例契约、基础设施和纯值规则，但DDD不得通过转调原结构化Service来冒充领域实现。

## 4. 运行支撑的边界

账号口令与Bearer索引是现有认证支撑，不新增核心凭证实体；当前RBAC自身需要账号登录，不照搬示例课程项目的“外部统一身份、不保存本地口令”。最小日志、导入来源、首次授权回执同样是运行支撑，不进入六实体核心ER。

认证支撑、日志端口、Excel读取可共用；RBAC有效授权、范围与完整K仍是本项目核心业务规则，两套实现必须保持同一语义。领域模型、Chen ER和物理表结构分别回答业务行为、概念联系和存储约束，三者不互相代替。

## 5. 统一语言与规则表达

| 术语 | 精确定义 |
| --- | --- |
| 账号 | 一个User及其口令/状态，工号和手机号两个入口共享，不按登录方式复制User |
| 可见部门 | 可信组织树中本人部门及其后代；响应中的根投影不改变实际归属 |
| 有效Permission集合 | 启用用户经启用角色获得的启用权限，所属系统启用；角色候选检查保留跨系统事实 |
| 有效API集合 | 上述权限显式映射的同系统启用API，以方法+服务端模板去重后OR判定 |
| 可授予角色 | 启用角色的全部有效Permission ID为操作者本系统有效Permission ID的子集 |
| 完整维护者 | 启用、直属已核实共同根且一个人覆盖完整K的User，不由名称或初始来源推断 |

记D(u)为u部门子树，P_all(u)为u在所有启用系统的有效Permission ID集合，A(u)为本RBAC同系统实际API集合。目标人员v的管理须先具具体操作API，再检查department(v)∈D(u)。候选角色r满足P_all(r)⊆P_all(u)，其中保留其他启用系统的有效权限，不能先过滤成空集合；逐系统权限映射只贡献该系统API，不跨系统拼接。

阶段3新增需求R23—R28的目标规则：非系统管理员还须满足目标级别严格低于本人；本人、同级、上级只读，系统管理员仍受实际API和完整维护者保护。部门新增的父级∈D(u)，局部改名/删除目标∈D(u)且非本人部门；删除仅空部门且非根，无层级调整。自定义角色不会提升操作者级别，默认仅管理员可授及维护其持有者。业务系统矩阵是参考，查看本人/编辑本人不变成无条件权限；实际数据约束和API集成仍待业务系统契约。以上当前仅在原型演示，正式服务尚未同步。

若M为启用且直属可信根的用户集合，则必须存在u∈M使K⊆A(u)。不能把M全体API并集覆盖K视为满足；日志读取则只检查该用户的日志API及根条件，不附加完整K。

## 6. 命令、行为与一致性

| 用例命令（目标语义名） | 领域行为 | 应用服务额外协调 |
| --- | --- | --- |
| ReplaceUserRoles | 替换明确roleIds集合 | 人员范围、逐角色有效Permission子集、自身/管理员限制、根锁和K |
| DisableUser / TransferUser | 停用；改变departmentId并保持身份与角色 | 原/目标双范围，最新操作者资格及K |
| CreateRole / UpdateRole | 创建空角色、改名、启停 | 编码唯一、共同根、实际API、共享影响与K |
| ReplaceRolePermissions | 独立替换完整跨系统permissionIds | 已登记系统/启用/存在性、共同根、根锁与K；切换显示不清空其他系统 |
| UpdatePermission / UpdateApi | 改允许字段或启停 | 跨节点同系统、无环、按钮无子及K |
| ReplacePermissionApis | 替换明确apiIds集合 | 同系统、可保留停用项，根锁与K |

以上命名用于解释目标职责，不宣称已有这些Command类。领域对象只处理掌握的状态与规则；需要多个对象的事实由领域策略接受明确输入，不让实体隐式访问仓储或HTTP。权限校验与锁后事实读取由应用用例组合，持久化适配器不得替代业务判断。

相关写在同一个本地数据库事务完成，稳定根行作为共同锁点。取锁后重读身份/授权/范围，执行领域行为，持久化并检查K；任何拒绝或故障回滚状态和关联。查询只读；日志记录可独立事务，不用于补偿业务成功或失败。

## 7. 生命周期与事件取舍

| 对象 | 状态变化 | 保留与即时效果 |
| --- | --- | --- |
| User | 初始启用→停用；部门/角色可独立变化 | 停用保留关系、使旧管理身份失效；本轮不提供恢复/删除接口 |
| Role | 启用↔停用 | 保留权限和用户关联；下次管理请求重算 |
| Permission / ApiResource | 启用↔停用 | 保留映射；父节点状态不代替子节点直接授权判断 |
| Department | 首次导入→新增下级/改名/删除空节点 | 类型固定，不调整层级；删除保留来源墓碑且不再参与范围 |
| ApplicationSystem | 本轮仅RBAC目录读取 | 演示系统不进入正式初始化，课程接入暂不考虑 |

没有必须异步完成的业务流程，本轮不引入事件总线、Outbox或分布式最终一致性。最小鉴权日志是运行记录，不冒充完整领域事件或变更审计。后续确有跨系统事件需求时另行评审。

## 8. 模型到设计的追溯

R01—R06落在身份、组织及初始化来源；R07—R09落在登录和有效授权策略；R10—R12落在范围与User行为；R13—R15落在共享Role/Permission/API及跨聚合维护者不变量；R16/R20由日志与安全适配支撑。关系和字段见数据库文档，用例及事务装配见后端设计。

后续DDD实施需复核聚合加载规模、仓储端口、批量查询及锁后一致事实，不把全部授权图加载进单个聚合。此为待审核目标设计；本次不创建DDD类，不据文档结构宣称已达到DDD实现要求。

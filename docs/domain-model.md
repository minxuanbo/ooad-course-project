# 领域模型与业务规则

本文表达RBAC统一业务概念及DDD领域边界。structured与DDD在同一工程内独立实现业务规则；装配、仓储及用例切片见[后端设计](backend-design.md)。领域仓储仅使用领域模型输入输出，不复用公共Command/Result。需求依据为[需求说明](requirements.md)，既有Chen ER见[数据库设计](database-design.md)。

## 1. 统一业务模型

本RBAC构成一个有界上下文。身份、组织、人员、授权目录与初始化是内部模块，不据此新增微服务或将每张表视为独立子域；日志、来源及回执为运行支撑。

| 业务概念                  | 责任、行为与不变量                                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 用户User                  | 单一内部身份、一个所属部门、零到多个角色；分配角色、停用、调动保持同一id。工号/手机号定位同一账号，不按姓名唯一定位。 |
| 角色Role                  | 具有显式来源分类的权限集合；部门自定义须有所属部门，应用预置须有来源应用；可改名/启停/整体替换权限，编码稳定。停用不删除关联，恢复后按当前资源状态重算。                    |
| 权限Permission            | 同一系统的菜单、按钮或通用API权限；维护父级、类型、有效状态及显式API映射。父菜单组织展示，可显式映射自己的读取API，不隐含子按钮写权限。                           |
| API资源ApiResource        | 单一系统的方法+路径模板，表达后端操作入口。多个权限可覆盖同一API，以有效链OR判定。                                    |
| 应用系统ApplicationSystem | 权限与API的归属和有效性边界；目录从数据库已登记应用及状态读取；默认初始化只登记rbac，课程等应用独立配置。                                         |
| 部门Department            | 总公司/分公司/部门/项目的层级节点；定义人员归属与子树范围，不直接给人授予权限。                                       |

系统管理员的人员保护例外及部门本级维护资格取决于有效基础级别5和可信根范围，操作仍须对应实际API权限；“完整维护者”另要求同一启用User覆盖全部K，是写后保底业务谓词。二者不单列实体或管理员字段，也不按角色名称判断。首次admin只是初始化来源；其他用户可通过合法授权取得相同资格，资格失效后按最新事实处理。单次操作不要求该操作者本人覆盖完整K，但相关写后必须至少保留一名完整维护者。

## 2. 核心业务判定

有效API集合由用户所持启用且部门适用的角色获得，用户、权限、API和所属系统均启用且CONNECTED；计划授权集合保留PENDING有效权限，用于完整子集检查。具体操作先检查该API，再检查人员范围或共同根范围。人员角色候选以有效Permission ID全集作子集比较，不能仅比较API路径，也不能丢弃外系统部分后继续授予。

人员归属决定可管理子树：总公司领导归根后覆盖所有分公司，分公司领导仅覆盖该分公司及后代。组织位置只约束范围；领导/经理称谓不授予操作权限。

全局维护保护是跨对象不变量：相关写提交后至少存在一个启用、直属可信根、有效基础级别为5的用户，具有有效RBAC登录资格并独自覆盖完整17项K。角色、权限、映射、API、人员角色、人员状态和调动都可能影响此结论，因此不能把检查局限在单个Role实体内。

## 3. DDD聚合与依赖

| 类型              | 自身状态与行为                                                                                                   | 跨聚合所需事实                          |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| User              | 内部ID、工号/手机号、哈希、姓名、只读职位、Department快照、启用、Set<Role>；replaceRoles/disable/transfer              | 操作者/目标级别与范围、角色有效权限、K  |
| Role              | code稳定、name、enabled、managementLevel、type、ownerDepartment、application、Set<Permission>；custom/departmental/revise/replacePermissions | 权限存在/启用/已登记应用、编码唯一、K       |
| Permission        | ApplicationSystem、parentId、type、enabled、Set<ApiResource>；revise/replaceApis                       | 同系统树无环、BUTTON无子、映射同系统、K |
| ApiResource       | 系统、方法/模板只读、enabled；changeAvailability                                                                      | 系统状态和K                             |
| Department        | 稳定code、parentId、type、name、deleted；child/rename/tombstone，变更前由OrganizationPolicy核验相关不变量       | 可信根与范围、同父名称、人员/下级存在性 |
| ApplicationSystem | 稳定code、名称、启用与接入事实；revise返回新值                                                                                     | 目录登记、逻辑移除/恢复、有效授权链同系统边界及维护者保护    |

领域record保存只读领域快照：User含Department与Set<Role>，Role含Set<Permission>，Permission含ApplicationSystem与Set<ApiResource>，不嵌入JPA对象。关系集合返回只读副本，替换行为明确增删，不通过公开setter任意修改权限关系。来源导入通过受控reconstitute或factory建立完整快照，不调用运行时HTTP补造数据。User只包含自身已分配角色快照，不包含全公司员工；Role不持有所有用户。关联事实由仓储批量装配，跨对象不变量仍由策略和应用用例协调。

领域状态/属性常量由对应对象以public static final声明：Role归口DEFAULT_LEVEL、PROJECT_MANAGER_LEVEL、DEPARTMENT_MANAGER_LEVEL、COMPANY_LEADER_LEVEL、ADMIN_LEVEL五基础级别，FIRST_MANAGER_LEVEL引用PROJECT_MANAGER_LEVEL；自定义角色的managementLevel为空。InitialAuthorizationPolicy引用Role的级别常量进行首次分类。Department归口四种类型，Permission归口MENU/BUTTON/API，ApplicationSystem归口RBAC系统编码。应用/领域不引用公共协议枚举作为自身状态，也不按角色名称猜级别；应用Mapper在领域取值与现有DepartmentType等协议值间显式转换。布尔启用状态保持其既有语义，不虚构额外生命周期。

UserKey、RoleKey、PermissionKey、ApiKey、DepartmentKey等不可变标识只用于领域/仓储边界的类型安全；HTTP仍为正安全整数，工号仍为字符串。PageWindow、DepartmentScope、ApiOperation、UserCriteria、RoleCriteria、AuthorizationFacts、OrganizationFacts、DepartmentUsage、MaintenanceFacts等值/事实都归domain.model；直接同字段不可变转换可使用0.0.2构造器映射并接收新值；领域业务工厂及跨层关联装配显式处理，不写final字段。

跨聚合策略在model.policy：AuthorizationPolicy逐链计算有效Permission/API及OR，按显式映射计算，不把父菜单当继承；RoleAssignmentPolicy同时检查目标保护、授予上限及完整有效Permission子集，新增/删除逐项验权，现有不可改角色可锁定保留，自定义角色不冻结人员；OrganizationPolicy核实来源根并计算有效子树/合法父子，以requireNonRoot保护可信根、requireEmpty拒绝存在人员、下级或所属角色的删除、requireUnique保证同父有效部门名称唯一；MaintenancePolicy判断一个启用、可信根、级别5的用户独自覆盖K，不把多人权限拼接。策略接受明确事实，不访问仓储、HTTP、Spring或全局缓存。

DDD仓储位于service.ddd.domain.repository，Infrastructure实现适配与装配；应用只依赖领域模型/仓储及公共用例抽象。事务、端口签名及复杂读模型见后端设计第4、6、9章。

## 4. 运行支撑的边界

首次接入的本部教师、分公司学生和双系统同一管理员是独立接入初始化的数据分配，不新增RBAC领域实体或职位推权。Teacher/Student及其user_id绑定只在课程系统建立；应用角色保持配置数据。后续组织调动或手动授撤角色不因重复初始化被自动恢复。

账号口令与Bearer索引是现有认证支撑，不新增核心凭证实体；当前RBAC自身需要账号登录，不照搬示例课程项目的“外部统一身份、不保存本地口令”。最小日志、导入来源、首次授权回执同样是运行支撑，不进入六实体核心ER。

认证支撑、日志端口、Excel读取可共用；RBAC有效授权、范围与完整K仍是本项目核心业务规则，两套实现必须保持同一语义。领域模型、Chen ER和物理表结构分别回答业务行为、概念联系和存储约束，三者不互相代替。

## 5. 统一语言与规则表达

| 术语               | 精确定义                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------- |
| 账号               | 一个User及其口令/状态，工号和手机号两个入口共享，不按登录方式复制User                                   |
| 可见部门           | 可信组织树中本人部门及其后代；响应中的根投影不改变实际归属                                              |
| 有效Permission集合 | 启用用户经启用角色获得的启用权限，所属系统启用；覆盖所有已登记应用；角色所含未登记应用即使停用也不允许通过过滤后授予      |
| 有效API集合        | 上述权限显式映射的同系统启用API，以方法+服务端模板去重后OR判定                                          |
| 可授予角色         | 启用角色满足固定授予级别上限，全部有效Permission ID为操作者全部已登记应用有效集合子集；目标人员另受严格级别保护 |
| 完整维护者         | 启用、直属已核实共同根、有效基础级别5且一个人覆盖完整K的User，不由名称或初始来源推断                    |

记D(u)为u部门的有效子树，P(u)为u在所有已登记启用应用、启用角色下的有效Permission ID集合（含无API映射菜单），A(u)为本RBAC同系统实际API集合。目标人员v的管理先具具体操作API，再检查department(v)∈D(u)。候选角色同时满足固定授予级别及P(r)⊆P(u)；不同登记应用的有效权限同样参与子集，不因只比较RBAC API而漏过。

人员与部门保护规则：非系统管理员还须满足目标级别严格低于本人，本人、同级、上级只读；系统管理员例外仍受实际API、范围及完整维护者保护。自定义角色不提升操作者级别，全局/应用关联仅可信根有效五级管理员可授，部门关联由所属或上级范围内领导按完整权限子集授撤，但可在原人员范围内维护较低级持有人，锁定原样保留项不算重新授予。部门新增父级∈D(u)，局部改名/删除须为严格下级；删除仅空且非根，类型固定，无层级调整。删除保留来源墓碑，不参与有效子树。两套实现均使用当前事务的角色与部门事实执行上述规则。

18业务系统及原表矩阵由独立首次配置进入正式计划授权，默认PENDING；运行期登录、短码和API通行仍失败关闭。课程系统按R29显式接入老师已有身份协议和真实API，不自行设计课程业务接口；沿用同一六实体模型，课程数据仍只在老师数据库。

## 6. 命令、行为与一致性

| 用例命令（目标语义名）                                 | 领域行为                                   | 应用服务额外协调                                             |
| ------------------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------ |
| ReplaceUserRoles                                       | 替换明确roleIds集合                        | 人员范围、逐角色有效Permission子集、自身/管理员限制、根锁和K |
| DisableUser / TransferUser                             | 停用；改变departmentId、保持身份并撤下不适用部门角色     | 原/目标双范围，最新操作者资格及K                             |
| CreateRole / UpdateRole                                | 创建空角色、改名、启停                     | 编码唯一、共同根、实际API、共享影响与K                       |
| CreateDepartment / RenameDepartment / DeleteDepartment | 新增合法下级、仅改名、删除空节点并保留墓碑 | 父/目标范围、类型、重名、无人无下级、根保护及共同锁          |
| ReplaceRolePermissions                                 | 独立替换完整已登记应用permissionIds             | 已登记应用/启用/存在性、共同根、根锁与K；候选页不截断完整集合    |
| UpdatePermission / UpdateApi                           | 改允许字段或启停                           | 跨节点同系统、无环、按钮无子及K                              |
| ReplacePermissionApis                                  | 替换明确apiIds集合                         | 同系统、可保留停用项，根锁与K                                |

以上命名用于解释目标职责，不宣称已有这些Command类。领域对象只处理掌握的状态与规则；需要多个对象的事实由领域策略接受明确输入，不让实体隐式访问仓储或HTTP。权限校验与锁后事实读取由应用用例组合，持久化适配器不得替代业务判断。

相关写在同一个本地数据库事务完成，稳定根行作为共同锁点。取锁后重读身份/授权/范围，执行领域行为，持久化并检查K；任何拒绝或故障回滚状态和关联。查询只读；日志记录可独立事务，不用于补偿业务成功或失败。

## 7. 生命周期与事件取舍

| 对象                     | 状态变化                           | 保留与即时效果                                          |
| ------------------------ | ---------------------------------- | ------------------------------------------------------- |
| User                     | 初始启用→停用；部门/角色可独立变化 | 停用保留关系、使旧管理身份失效；不提供恢复/删除接口 |
| Role                     | 启用↔停用                         | 保留权限和用户关联；下次管理请求重算                    |
| Permission / ApiResource | 启用↔停用                         | 保留映射；父节点状态不代替子节点直接授权判断            |
| Department               | 首次导入→新增下级/改名/删除空节点  | 类型固定，不调整层级；删除保留来源墓碑且不再参与范围    |
| ApplicationSystem        | 新增PENDING、修改资料、逻辑移除与恢复        | 默认万人初始化仅RBAC；独立首次配置登记18项PENDING业务目录及CONNECTED课程，运行通行另查接入状态 |

没有必须异步完成的业务流程，不引入事件总线、Outbox或分布式最终一致性。最小鉴权日志是运行记录，不冒充完整领域事件或变更审计。后续确有跨系统事件需求时另行评审。

## 8. 模型到设计的追溯

R01—R06落在身份、组织及初始化来源；R07—R09落在登录和有效授权策略；R10—R12落在范围与User行为；R13—R15落在共享Role/Permission/API及跨聚合维护者不变量；R16/R20由日志与安全适配支撑；R29落在通用ApplicationIdentityUseCase及各策略独立投影，R30规定中文显示名与稳定编码分离。关系和字段见数据库文档，用例及事务装配见后端设计。

授权事实按当前用户读取，人员页批量读取当页角色。域仓储和锁后回归证据见测试与验收说明。

应用身份只投影当前受众下的有效角色编码和权限，不增加课程实体。Permission.type的API项要求非空有效映射；MENU/BUTTON保留展示和资格控制用途。自定义角色不冻结User，角色差集校验及锁定项规则见R27。

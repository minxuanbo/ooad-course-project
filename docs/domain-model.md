# 领域模型与业务规则

版本：1.0。本文先表达业务概念，再提出DDD边界；当前代码仍是结构化Service与JPA实体，本文不声明DDD已落地。需求依据为[需求说明](requirements.md)，既有Chen ER见[数据库设计](database-design.md)。

## 1. 统一业务模型

| 业务概念 | 责任、行为与不变量 |
| --- | --- |
| 用户User | 单一内部身份、一个所属部门、零到多个角色；分配角色、停用、调动保持同一id。工号/手机号定位同一账号，不按姓名唯一定位。 |
| 角色Role | 全局共享的权限集合；可改名/启停/整体替换权限，编码稳定。停用不删除关联，恢复后按当前资源状态重算。 |
| 权限Permission | 同一系统的菜单或按钮；维护父级、类型、有效状态及显式API映射。父菜单负责展示，不隐含子权限。 |
| API资源ApiResource | 单一系统的方法+路径模板，表达后端操作入口。多个权限可覆盖同一API，以有效链OR判定。 |
| 应用系统ApplicationSystem | 权限与API的归属和有效性边界；当前管理目录为rbac，外系统目录不能进入本轮维护。 |
| 部门Department | 公司/分公司/部门的层级节点；定义人员归属与子树范围，不直接给人授予权限。 |

“全局管理员”是某个User在当前授权与组织状态下满足完整K的业务谓词，不是实体、字段或固定角色名称。首次admin只是初始化来源；其他用户可通过合法授权形成相同能力，失效后也不再满足该谓词。

## 2. 核心业务判定

有效API集合由用户所持启用角色的启用权限映射得到，且用户、API及其同一所属系统均启用。具体操作先检查该API，再检查人员范围或共同根范围。人员角色候选以有效Permission ID全集作子集比较，不能仅比较API路径，也不能丢弃外系统部分后继续授予。

人员归属决定可管理子树：总公司领导归根后覆盖所有分公司，分公司领导仅覆盖该分公司及后代。组织位置只约束范围；领导/经理称谓不授予操作权限。

全局维护保护是跨对象不变量：相关写提交后至少存在一个启用根用户，独自覆盖完整17项K。角色、权限、映射、API、人员角色、人员状态和调动都可能影响此结论，因此不能把检查局限在单个Role实体内。

## 3. DDD拟议聚合与依赖

以下为目标设计，后续实施前按真实写场景复核；不为每张数据库表机械生成一个领域服务。

| 拟议聚合/对象 | 边界与标识引用 |
| --- | --- |
| User聚合 | 用户资料、状态、departmentId与显式roleIds；通过领域行为变更，不把Role或Department的可编辑JPA对象直接嵌入。 |
| Role聚合 | 稳定编码、名称、状态、显式permissionIds；Role不管理所有用户，也不持有整个授权图。 |
| Permission聚合 | 系统标识、父标识、类型、状态和显式apiIds；跨节点无环、同系统及按钮子节点约束由领域规则结合仓储事实检查。 |
| ApiResource聚合 | 系统标识、稳定方法/模板、启用状态；状态变更须参与全局维护保护。 |
| Department与ApplicationSystem | 保持稳定标识及业务约束；当前只读场景可采用读取模型，不为未要求的组织/系统CRUD增加命令。 |
| 值对象 | 候选包括部门范围、方法/路径组合、有效权限集合、角色分配集合；只有封装实际规则时才引入，不包装所有字符串和ID。 |
| 领域策略 | 有效授权计算、角色可授予判断、人员变更限制与完整维护能力判断；输入业务事实，输出业务结论，不依赖HTTP/JPA。 |

同一根锁下的业务事务由应用服务编排：读取锁后最新事实→调用领域规则/行为→通过仓储端口持久化→检查完整K→提交。跨聚合保护使用同一事务与稳定锁点，不引入消息最终一致性、分布式事务或把全数据库装成一个巨大聚合。

DDD仓储接口位于领域/用例端口，Infrastructure实现JPA适配与装配；应用服务不得引用EntityManager、JpaRepository或JPA Entity。结构化与DDD可以共享错误码、用例契约、基础设施和纯值规则，但DDD不得通过转调原结构化Service来冒充领域实现。

## 4. 运行支撑的边界

账号口令与Bearer索引是现有认证支撑，不新增核心凭证实体；当前RBAC自身需要账号登录，不照搬示例课程项目的“外部统一身份、不保存本地口令”。最小日志、导入来源、首次授权回执同样是运行支撑，不进入六实体核心ER。

认证支撑、日志端口、Excel读取可共用；RBAC有效授权、范围与完整K仍是本项目核心业务规则，两套实现必须保持同一语义。领域模型、Chen ER和物理表结构分别回答业务行为、概念联系和存储约束，三者不互相代替。

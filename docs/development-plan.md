# RBAC双实现交付计划

本计划依据用户最新确认，目标是先完成本RBAC的structured/ddd两套代码及共用前端。课程系统指老师Gitee上的course-project-mgt，等老师另给接入要求；当前不启动T14/T15，也不自行新增课程业务。

## 1. 当前基线

T13已随PR #28合入ffc7ceb，记录了当前结构化后端的验收。当前分支已将结构化代码迁入backend并按service/structured、service/port和infrastructure分层，没有DDD实现或策略开关；正式前端只有登录、日志兼容与最小外壳。此前T13是阶段基线，新改动仍需重新验证，不能沿用其结果宣称双实现/新前端通过。

## 2. 已确认顺序

| 阶段 | 交付 | 审核关口 |
| --- | --- | --- |
| 1 文档清理/完善 | 唯一需求、领域/数据库、前后端、API、初始化、测试及资料归类 | 2026-11-13用户审核同意，PR #29已合入；进入阶段2 |
| 2 结构化代码整理 | 参照老师分层，抽取共用用例/持久化边界，分批修复格式、职责及CloneFactory遗漏 | 当前阶段；写代码skill、双轴审核、真实回归及版本化结果；只交付结构化实现 |
| 3 新前端原型/API审核 | RBAC全量页面、权限/范围差异、表单/空/错/并发反馈及页面接口对照 | 新原型经用户审核，必要契约变更先确认；现存prototype仅参考 |
| 4 正式前端更新 | 按获批原型实现并与结构化后端真实联调 | 页面行为、真实API/范围、错误、键盘/窄屏检查 |
| 5 DDD实现与文档 | 同仓库同应用，选定一套Service，分享API/数据库/前端，领域仓储适配 | 独立领域行为、事务/锁/回滚、两策略同一契约，禁止转调structured冒充DDD |
| 6 RBAC双实现总验收 | 分别运行两策略、隔离数据库、同一前端及完整端到端 | 业务结果、范围、错误、持久化状态和并发一致；明确未完成的课程接入 |

阶段2先确定公共边界，阶段5再编码DDD。没有另行授权时不跳过用户原型/文档审核，不自动合并或启动下一阶段。

## 3. 文档维护方式

设计文档写目标及职责，当前实现/验收单独标状态；实施后更新实际目录、配置和证据。需求变更同步需求与API，模型变更同步领域/ER/物理约束，接口变更同步OpenAPI/页面对照/测试，不保留相互竞争的旧规范。

阶段1变更见[原审核指南](review-guide.md)；当前阶段2实际边界及文件/测试命名见[代码归类](code-organization.md)。部署待新增服务器方案，当前不实施。

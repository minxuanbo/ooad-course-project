版本：1.0；整理日期：2026-11-12。本文是当前业务需求入口，描述应满足的行为，不作为实现完成声明。

冲突按老师业务要求及用户后续明确确认处理。历史需求规格说明书、旧原型和旧代码不覆盖本说明；历史证据保留在[legacy](legacy/README.md)与[整改记录](rbac-rectification/README.md)。待确认的课程系统业务不据示例项目自行补齐。

系统目标是统一维护用户、角色、菜单/按钮与API的授权关系，以组织树限定人员管理范围。RBAC管理系统与Excel中的“系统管理后台”是两个业务系统，后者的五角色业务矩阵不能直接当作本RBAC管理端权限。未来课程系统是另一受控业务系统；structured/ddd是同一业务的实现方式，两个维度彼此独立。

## 2. 数据与初始化要求

| 编号 | 要求 |
| --- | --- |
| R01 | 保留六个核心实体：User、Role、Permission、Department、ApplicationSystem、ApiResource；公司、分公司均为部门树节点，不建独立全局账号实体、管理员属性或独立管理范围表。 |
| R02 | 用户必须属于一个部门。人员管理范围是本人部门及后代；共同根须由来源映射和真实树核实，部门名称或任意parentId为空不能作为全局资格。 |
| R03 | 原始组织111节点，导入仅将“公司领导”合并到“总公司”，其10人归根，目标110部门；10000员工加独立admin共10001账号，根直属11人。保留原件、源行、六列、文件摘要与新ID映射，不迁旧ID/哈希/状态/授权。 |
| R04 | username就是工号，来自Excel“用户名”；phone来自“电话号码”，是同一账号另一登录入口。工号唯一，手机号可空、非空值唯一；来源导入拒绝跨用户标识碰撞。不增加employee_no、标识注册表或第三种别名。 |
| R05 | 员工全部启用，员工统一初始口令与管理员独立口令分别来自必填部署配置，各账号独立BCrypt盐；默认管理员账号名admin，可显式配置。秘密不进入源码、命令参数或报告。 |
| R06 | 组织账号导入与首次授权分开。首次按已确认且经来源核对的清单批量授予五角色；预览只读，实际授权整批事务；重复执行不覆盖后续状态、部门、口令或授权调整，来源变化或不一致拒绝。 |

首次清单人数及业务能力如下。岗位分类只用于这一次已确认清单，不作为运行时鉴权或后续调动自动改角色的依据。

| 初始角色 | 人数 | 本RBAC系统的初始能力 |
| --- | ---: | --- |
| 系统管理员 | 1 | 独立admin，完整维护及日志查询 |
| 公司领导 | 64 | 总公司/分公司直属领导；范围内人员查询、角色分配、停用与调动 |
| 部门经理 | 106 | 部长、副部长；同上，范围为本人部门及后代 |
| 项目经理 | 72 | 项目经理、副经理；同上，范围为本人部门及后代 |
| 普通员工 | 9758 | 无本RBAC管理操作权限，拒绝登录管理端 |

10名总公司领导合并归根后，其范围覆盖整棵组织树；仍不因“领导”称谓获得角色定义、资源维护或日志权限。三种人员管理角色均不含这些全局维护能力。后续用户可拥有零到多个角色。

## 3. 登录、授权与管理行为

| 编号 | 可验收的业务要求 |
| --- | --- |
| R07 | 单一account/password入口精确匹配工号或手机号；必须定位唯一用户，同用户两字段同值视为一人。未知、跨用户歧义、错口令、停用统一401 LOGIN_FAILED；不得按号码长度猜输入类型。 |
| R08 | 账号/口令通过后，至少有一项本系统已登记且有效的管理API才可登录；无角色、空角色、普通员工、仅父菜单或仅外系统权限拒绝。已有身份每次管理请求仍重新鉴权。 |
| R09 | 有效授权沿启用User→Role→Permission→同系统启用ApiResource及ApplicationSystem计算，按方法与服务端路径模板匹配。多角色/多权限按OR；父菜单不隐含子按钮API，父节点停用不级联撤销直接授予子项。 |
| R10 | 人员查询先限定部门范围，再执行部门子树、姓名/工号搜索、状态、分页及同条件计数；未知可见对象404，范围外对象403。部门树不得泄露范围外父节点/兄弟节点。 |
| R11 | 选人后可查看当前角色和受限候选，整体替换角色；角色的全部有效权限必须是操作者有效权限的子集，不得把外系统权限过滤掉后当作空角色授出。部门操作者不能改自身授权/部门或有效全局管理员。 |
| R12 | 停用账号后现有身份不能继续管理，再次登录拒绝。调动要求原部门与目标部门均在操作者范围内；保持同一用户身份与角色，后续请求按新部门范围判断。 |
| R13 | 全局角色/资源目录读写须共同根及对应实际API权限。角色支持查询、新建空权限定义、改名、启停、整体替换权限；不扩展删除、继承、审批或版本。 |
| R14 | 资源维护限定本系统目录、权限parentId/type/enabled、API enabled及权限—API整体映射。按钮无子节点、父子同系统、树无环、映射同系统。系统/code/name及API method/path不提供本轮编辑入口。 |
| R15 | 相关写入共用可信根锁，锁后重新检查当前身份、权限及范围；写后至少保留一名直属共同根、启用且独自具备完整K的有效用户。同用户多角色可汇总，不同用户不能拼接成一名管理员。冲突和故障全回滚。 |
| R16 | 最小鉴权日志记录真实登录/鉴权允许及拒绝，可筛选和快照游标分页。查询同时要求日志API及共同根，完整K不是查询前置；部门账号即使误授该API也拒绝。不含归档、导出或完整变更审计。 |

K包含角色维护、角色权限配置、人员角色分配、资源与映射维护及其必要查询，共17个方法/路径模板；日志、停人、调动不在K内。精确定义沿[契约2.3](api-contract.md#23-精确目录与管理员保护-k)，不得用角色名或权限编码存在代替实际API覆盖。

## 4. 前后端及技术要求

| 编号 | 要求 |
| --- | --- |
| R17 | 前端应包含登录、部门人员、人员角色/停用/调动、角色权限、资源映射、日志必要交互；按实际操作与范围显示入口，但后端独立执行权限判断。完整设计见[前端设计](frontend-design.md)。 |
| R18 | 先原型、后API契约、后实现；共享统一响应、requestId、稳定错误码、输入校验和分页。前端交互原型不能冒充真实HTTP或界面完成证据。 |
| R19 | Java21、Spring Boot、Spring Data JPA、AOP、Service读写声明式事务及老师真实CloneFactory；Controller仅适配，持久化错误在写边界翻译。禁止旧JDBC业务链路复活。 |
| R20 | 最小日志/AOP不得输出口令、令牌、Authorization、原始手机号登录输入、SQL、请求体或完整隐私对象；安全失败返回可追踪requestId，不泄露内部异常。 |
| R21 | 同仓库规划structured与ddd两套业务实现，共享API/数据库契约，通过配置选择；同一套行为契约分别验证两种实现。DDD应用层依赖抽象领域仓储，领域对象不依赖JPA/MVC。当前只有结构化实现，DDD实施另行启动。 |
| R22 | 初始化、运行与验收使用明确隔离库，不修改原业务库、Excel或历史日志；启动仅校验结构，不自动建旧表、导入或重授角色。构建、初始化与限制须可复现。 |

性能只约束万人场景必须分页、数据库范围筛选及避免候选全量/N+1，不虚构响应时间、吞吐量或SLA。覆盖率配置保留，用户确认本轮JaCoCo不作为阻塞；功能测试通过不能表述为100%覆盖。

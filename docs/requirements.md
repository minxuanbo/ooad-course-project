## 3. 登录、授权与管理行为

| 编号 | 可验收的业务要求 |
| --- | --- |
| R07 | 单一account/password入口精确匹配工号或手机号；必须定位唯一用户，同用户两字段同值视为一人。未知、跨用户歧义、错口令、停用统一401 LOGIN_FAILED；不得按号码长度猜输入类型。 |
| R08 | 账号/口令通过后，至少有一项本系统已登记且有效的管理API才可登录；无角色、空角色、普通员工、仅父菜单或仅外系统权限拒绝。已有身份每次管理请求仍重新鉴权；授权变更提交后的新请求立即按最新权限判断，无需重新登录，详见3.1。 |
| R09 | 有效授权沿启用User→Role→Permission→同系统启用ApiResource及ApplicationSystem计算，按方法与服务端路径模板匹配。多角色/多权限按OR；父菜单不隐含子按钮API，父节点停用不级联撤销直接授予子项。 |
| R10 | 人员查询先限定部门范围，再执行部门子树、姓名/工号搜索、状态、分页及同条件计数；未知可见对象404，范围外对象403。部门树不得泄露范围外父节点/兄弟节点。 |
| R11 | 选人后可查看当前角色和受限候选，整体替换角色；候选及保存同时满足R23授予级别和完整有效Permission子集，不能只比较API能力，不得先过滤外系统权限后当作空角色授出。目标人员另受R27保护。 |
| R12 | 停用账号后现有身份不能继续管理，再次登录拒绝。调动要求原部门与目标部门均在操作者范围内；保持同一用户身份与角色，后续请求按新部门范围判断。 |
| R13 | 全局角色/资源目录读写须共同根及对应实际API权限。角色支持查询、新建空权限定义、改名、启停、整体替换权限；不扩展删除、继承、审批或版本。 |
| R14 | 资源维护限定本系统目录、权限parentId/type/enabled、API enabled及权限—API整体映射。按钮无子节点、父子同系统、树无环、映射同系统。系统/code/name及API method/path不提供本轮编辑入口。 |
| R15 | 相关写入共用可信根锁，锁后重新检查当前身份、权限及范围；写后至少保留一名直属共同根、启用、有效基础管理级别为5且独自具备完整K的用户。同用户多角色可汇总，不同用户不能拼接成一名管理员。冲突和故障全回滚。 |
| R16 | 最小鉴权日志记录真实登录/鉴权允许及拒绝，明确事件时间、主体、目标、结果、原因及请求追踪信息，支持筛选、同条件总数和快照游标分页，详见3.2。查询同时要求日志API及共同根，完整K不是查询前置；部门账号即使误授该API也拒绝。不含归档、导出或完整变更审计。 |
| R23 | 增加明确角色授予级别：系统管理员可授全部角色；公司领导可授公司领导及以下；部门经理可授部门经理/项目经理/普通员工；项目经理只可授项目经理/普通员工。新建自定义角色默认仅系统管理员可授，持有自定义角色不会因此获得管理员级别；始终叠加R11当前RBAC权限子集和R02部门范围。 |
| R24 | 独立部门管理支持新增、改名、删除，不提供调整层级。系统管理员维护全公司；公司领导/部门经理/项目经理仅可改名或删除本人直属部门的严格下级，不能操作本人、上级、平级。新增父级可选本人部门或下级且须符合类型：总公司可建分公司/部门/项目；分公司可建部门/项目；部门只能建项目；项目不可建下级，不创建第二个总公司。仅无人且无下级的空部门可删，根不可删；新增不自动授予人员角色。名称先trim再验1—100字符，同一上级下不能重名；改名不改变ID、人员归属、职位、角色或范围，原Excel不改。每次仍须对应实际操作权限。 |
| R25 | 增加总览，展示当前可管理范围的人员总数、启用/停用人数、组织节点及下级分布，提供获准工作区快捷入口。系统管理员可见全公司，其他管理者仅见本人部门及下级；最近鉴权活动仍须日志API和共同根，不向非根混入全局日志。 |
| R26 | 人员列表展示只读职位及当前已授角色摘要，职位来源为老师Excel“岗位”等已核实人事资料，不提供职位编辑或职位调动，也不因职位文本自动增减权限。角色摘要包含停用角色，明确标为“角色已停用”，账号列为“账号状态”；二者独立，停用角色保留关联但不贡献权限，不会自动停用持有者账号。进入分配抽屉仍读取完整当前角色和分页候选。 |
| R27 | 非系统管理员仅可修改级别严格低于本人的范围内人员；本人、同级、上级只读，角色调整/停用/部门调动全部受限。公司领导之间不因共享部门范围而相互修改。可按R23将下级授为本级，成功后按其最新级别保护。系统管理员例外仍须有效API、范围及完整维护者保护。自定义角色不提升操作者级别；仅管理员可授的自定义角色持有者也不能由局部管理员撤回。 |
| R28 | 原型中保留Excel18业务系统、115模块、359功能点和角色矩阵，仅演示跨系统权限控制能力，不是正式接入目录。原表“系统管理后台”不等于本RBAC。当前正式系统只初始化、配置和判定RBAC自身权限，不导入演示业务系统或其角色授权，也不提供其业务API、应用入口或原表模板套用。课程系统目前不考虑接入，未来需另行明确契约。原型中“全部”为同行其他角色明列操作并集；空白未规定不授权；view及本人限定保持原确认口径。 |

K包含角色维护、角色权限配置、人员角色分配、资源与映射维护及其必要查询，共17个方法/路径模板；日志、停人、调动不在K内。精确定义沿[契约2.3](api-contract.md#23-精确目录与管理员保护-k)，不得用角色名或权限编码存在代替实际API覆盖。

### 3.1 实时鉴权与撤权生效（R08、R09、R12、R15）

授权变化以事务成功提交为生效边界。管理员撤销人员角色、调整共享角色权限，或停用角色、权限、API及系统后，用户使用原登录身份发起的后续受控请求必须按最新有效授权及部门范围重新判断；不得等待重新登录、令牌过期、页面刷新或固定缓存周期才生效。事务失败或回滚不应产生部分撤权结果。

撤销一条授权链后，若用户已无其他有效授权授予该API，后续请求必须拒绝；若另一启用角色或权限仍合法映射同一API，应保留该有效访问能力，不能把撤销某个角色误当作撤销全部角色。账号停用后原身份不得继续管理，部门调动后按新部门子树判断，原范围不应继续有效。

例：员工同时持有角色A和B，只有A授予人员查询API。管理员撤销A并提交后，员工无需退出登录，再次调用人员查询API即应被拒绝；若B也有效授予该API，则仍可在当前部门范围内查询。

“立即生效”约束提交后的新请求，不承诺追溯取消已进入执行阶段的在途操作。等待共同根锁的管理写仍须在取得锁后重验最新身份、API及范围，不得凭取锁前的旧授权提交。前端应更新失效操作并展示拒绝结果，后端必须独立保证上述规则；本条不要求推送、强制刷新或新增会话实体。

### 3.2 鉴权日志记录与查询统计（R16、R20）

日志应记录真实登录成功/失败、未认证访问，以及受控请求鉴权的允许/拒绝；同一安全事件不应因过滤器、预检和AOP重复采集而重复计数。鉴权允许只表示通过访问控制，不等同于后续业务操作成功，HTTP状态应与鉴权结论分别记录。

| 信息类别 | 必须记录的信息 | 口径 |
| --- | --- | --- |
| 事件标识与时间 | 日志ID、事件时间 occurredAt、事件类型 eventType | 时间采用UTC；区分登录、未认证访问及鉴权事件 |
| 操作主体 | 用户ID userId、工号 username | 无法识别主体时允许为空；工号是账号字段，不复制手机号登录输入或其他未核实原始输入 |
| 访问目标 | 系统编码 appCode、权限编码 permissionCode、HTTP方法 httpMethod、请求路径 requestPath | 未定位权限时允许权限编码为空；路径不含查询串、口令或令牌，不将未知目标伪装成已授权目标 |
| 判定与响应 | 允许/拒绝 allowed、原因码 reason、HTTP状态 httpStatus | 记录真实鉴权结果和安全原因码，禁止用业务成功代替鉴权允许 |
| 请求关联 | requestId | 与接口响应关联，便于定位一次请求及其安全事件 |

查询应支持用户ID、工号、系统、允许/拒绝、事件类型及时间范围组合筛选；工号、系统、事件按精确值匹配，时间含开始、不含结束。结果按日志ID倒序并使用快照游标分页；每次继续查询仍须检查日志API权限及共同根资格。

统计项为当前筛选条件、同一快照内的匹配总数 total；它不是当前页条数，也不应随翻页缩小或因快照之外的新日志增长。界面可据已加载记录显示已加载条数和是否还有更多；修改筛选或分页批量须重新建立查询，刷新后才纳入新事件。具体字段类型及游标约定沿API契约。

当前明确日志记录、检索及匹配总数，不要求按日访问量、成功率、拒绝率等汇总报表。敏感信息限制沿R20；旧文档中的日志归档、导出及完整管理变更审计不随本次补充恢复。相关范围如有新要求，后续再调整需求和设计。

### 3.3 角色授予级别与权限子集（R11、R23）

原型首次数据及显式重置时，公司领导、部门经理、项目经理、普通员工四个基础角色应分别取得Excel对应列的业务操作和所需祖先菜单，不再以空业务权限开始；未知/无权限项不授予，“全部”沿R28并集口径。普通员工仍无本RBAC管理API，其他三角色保留已确认的人员/部门管理API。初始菜单为明确授予，不意味着父菜单继承子权限；之后手工修改应保留，新建自定义角色仍为空权限。

原表业务权限不是按职级逐级包含，因此R23只定义级别上限，不能保证本级以下每个角色都出现在候选中。上述是离线原型的演示口径。当前正式系统只按RBAC自身完整有效Permission子集过滤、保存复验，不初始化演示业务权，也不让其影响人员候选。例如公司领导缺少部门经理的一些编辑权限，初始状态不能完整授予该部门经理角色；应由系统管理员处理，不能绕过子集限制。

公司领导、部门经理、项目经理虽具有相同类型的人员管理API，也不能据此相互授予任意级别角色。级别是独立的授予约束，不代表权限继承，不扩大人员管理范围，不代替逐次实际API鉴权。

基础角色的授予级别使用明确元数据，不按角色名称、编码文本或职位猜测；改名不改变级别。操作者拥有多个启用角色时取其有效最高级别，再检查目标角色的全部有效Permission集合是否为本人有效集合的子集。自定义角色默认仅管理员可授，其持有者不自动升级。候选过滤与最终整体保存使用同一规则，不能绕过候选直接提交越级ID，也不能在提交时静默丢弃不合规的当前角色。

完整维护者保护仍须同一启用共同根用户实际覆盖K。在增加授予级别后，保留者还须具备完整角色恢复的授予级别，避免只有API入口却无法恢复基础管理员角色；级别本身不能代替实际K覆盖。阶段4将此约束纳入结构化后端；历史验收仍保持原版本口径。

### 3.4 部门层级展示及人数口径（R24）

部门目录按父部门、其整棵子树、下一同级部门的顺序显示；项目紧跟所属部门并缩进，不能沿数据创建顺序散列。搜索项目时保留范围内祖先路径及缩进，不展示范围外上级。直属人数只计算departmentId为当前节点的账号；总人数含全部下级及启用/停用账号。每个节点总人数=直属人数+各直接下级总人数，父子行不能再重复相加。此展示不修改组织归属、层级或人员数据。

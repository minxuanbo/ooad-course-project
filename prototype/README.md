# 离线交互原型 · 第六轮

2026-11-13；分支codex/interactive-prototype。基于已合入的PR #30，按用户第一轮反馈扩展；界面仍在评审中，尚未成为正式frontend。

## 直接打开

用现代Edge或Chrome双击[index.html](index.html)，无需启动服务、安装依赖、构建或连接后端。分发时保留同目录七个文件：index.html、styles.css、applications.js、catalog.js、model.js、pages.js、app.js。普通脚本按顺序加载，不用ES Module、接口请求、远端字体/CDN或浏览器存储。刷新、重置后还原演示数据。

人员及组织均为虚构演示数据：168名人员、15个初始组织节点及少量分页角色；业务权限目录只读提取自原Excel；不是原Excel人员，也不代表正式10001账号/110部门初始化。演示口令Demo@2026不能用于正式环境。

| 身份 | 账号 | 可见工作区 |
| --- | --- | --- |
| 系统管理员 | admin | 总览、部门管理、人员管理、角色与权限、资源与API、鉴权日志 |
| 公司领导 | SG000001或13800000001 | 第一分公司范围总览、部门管理、人员管理 |
| 部门经理 | SG000002 | 工程管理部及下级总览、部门管理、人员管理 |
| 项目经理 | SG000003 | 滨江项目部总览、部门管理、人员管理 |
| 普通员工 | SG000004 | 管理端准入拒绝 |

## 本轮改动

1. 总览：范围内人员/启用/停用/组织数量，下级人员分布及获准快捷入口；仅日志获准的共同根用户看到最近鉴权活动。
2. 部门管理：新增下级、改名、删除空部门。局部管理员可在本人或下级下新增，仅改删严格下级，不能操作上级或平级；本人节点不可改删，新增仍须类型允许：总公司可建分公司/部门/项目，分公司建部门/项目，部门只建项目，项目不可建下级。删除须无人且无下级，根不可删，无层级调整。
3. 人员管理：独立显示只读“职位”和“已授角色”；职位来自人事资料，不提供编辑或职位调动。角色摘要包括停用项，分配时仍独立读取完整集合。
4. 授予级别：系统管理员全部；公司领导本级及以下；部门经理为部门经理/项目经理/普通员工；项目经理为项目经理/普通员工。仍检查实际Permission子集及人员范围，不能按相同API能力越级。
5. 自定义角色默认仅系统管理员可授；名称修改不改变级别，其持有者不会自动成为管理员。角色新建为空权限，随后显式独立选权，无继承或删除。
6. 资源：本RBAC加原Excel18业务系统、115模块/359功能点，按系统看树/API/五角色原文矩阵。18业务系统未实现，API为空仅演示权限控制；后续仅课程管理系统实际接入。角色跨系统逐项选权保留完整集合，不提供模板套用；全部仅为本行其他角色操作并集，I340未规定不自动选。
7. 日志：组合筛选、同快照total、分批加载、刷新及脱敏详情；鉴权允许与后续400/404/409/500业务响应分别记录。没有归档、导出或按日汇总报表。

日志页查询/续批不读取无关部门树，返回人员页时由人员页重新读取。无筛选且期间无其他操作时，重新查询会纳入前一次日志查询自身的1条鉴权事件；改变每批条数本身不产生日志。同一快照继续加载时total保持不变，每次日志请求仍实时检查身份、日志权限及共同根范围。

全部导航按有效操作和共同根范围显示，级别用固定元数据约束角色授予，不用角色名称判断操作权限。完整维护者同时需要同一启用共同根用户覆盖K及拥有恢复基础管理员角色的授予级别；原型用内存回滚演示，不冒称真实事务锁。

## 建议体验

- admin登录，查看总览全部入口；把“滨江项目部”改名，再到人员页和总览核对同步。
- 人员页查看沈清禾SG000004的职位/角色；分配抽屉跨页选择、取消/放弃、清空确认及保存；职位始终只读。
- 四基础角色已按原表预置各系统业务权。切换管理者查看候选：级别只是上限，还须完整Permission子集，原表不逐级包含，所以本级以下角色未必全部可授；各身份组织树保持本人范围。
- 角色页新建自定义角色，再配置权限；只勾选父菜单不会自动选子权限。
- 尝试撤去管理员关键权限、停用关键API或清空关键映射，观察LAST_ADMIN_REQUIRED及草稿/数据回滚。
- 日志加载下一批，total与snapshot保持；修改筛选后须重新查询，不能将新条件串到旧游标。
- “原型评审”可模拟下一次读取/保存的网络、401/403/404/409/500错误，切换身份、慢加载、撤权或重置。该工具属于评审辅助，不进入正式产品。

## 与正式接口的差异

现有OpenAPI的角色、资源、人员写及日志接口维持原样。下列是用户新增需求的后续接口/模型设计待办，**当前没有修改正式OpenAPI、后端或物理表**：

| 新需求 | 后续需落实 |
| --- | --- |
| 职位与角色摘要 | 人员列表增加position及轻量roles摘要，保留人员范围；避免逐行N+1。职位源已有User.position，来源Excel“岗位”，不加编辑接口。 |
| 授予级别 | Role增加稳定级别元数据及默认自定义授予策略；候选/整体保存和最后维护者恢复条件统一落实。不根据名称/职位推断。 |
| 部门维护 | GET /api/departments、POST /api/departments、PATCH及DELETE /api/departments/{id}均为原型提案；需正式权限、范围、删除关联约束及导入映射兼容设计。 |
| 总览 | 确定范围内聚合查询契约或复用查询方案，权限/范围在服务端执行；不从全量人员前端计数。 |

原型满意后，再统一评审Schema、错误、约束及数据库迁移，随后进行正式实现和真实联调。本轮模拟方法不是后端接口证据，演示路径不应混入当前OpenAPI。

## 文件与检查

- applications.js：原Excel只读提取的本地业务矩阵，含来源SHA、原文及缺失项。
- catalog.js：RBAC演示目录与业务菜单/按钮映射，不含虚构业务API。
- model.js：内存身份、范围、级别、角色/资源、快照日志与回滚。
- pages.js：总览、部门、角色、资源、日志页面与交互。
- app.js：共用外壳、登录、人员及模态/请求状态。
- tests：离线加载、既有行为及本轮新需求检查。

在仓库根执行：

```text
node --check prototype/app.js
node --check prototype/pages.js
node --check prototype/model.js
node --check prototype/catalog.js
node --test prototype/tests/*.test.cjs
```

真实浏览器检查与审核记录见[原型评审](../docs/prototype-review.md)。用户满意前，不自行合并或启动正式前端/DDD/服务器部署。

本目录是仓库唯一原型，已替换早期四组页面及v2并行目录。部门按子树排序，项目紧跟所属部门并缩进；搜索保留可见祖先。“直属人数”不含项目，“总人数（含下级）”含项目及停用账号，父子人数不能重复相加。当前用户授权推送分支供组员审核，阶段4前后端更新等待小组确认。

## 第六轮重点体验

- SG000001登录，人员页查SG000008，同分公司领导仅查看，不能改角色、停用或调动。管理员可操作，完整维护者保护仍有效。
- 公司领导/部门经理/项目经理均可查看部门管理；新增仍须类型允许，部门只建项目，项目不能新增下级。本人节点不可改删；下级空节点可改名/删除，有人员或子节点不可删除。
- admin进入资源与API切换18业务系统，查看原表矩阵；这些系统未实现、API为空符合范围，后续实际只接入课程管理系统。成本管控系统第340行普通员工为“未规定”。
- 角色权限抽屉切换系统逐项勾选，其他系统不丢失，不提供原表模板套用。保存前可取消；18业务系统API为空符合范围，不设计其业务接口。
- 首次/重置时四基础角色按原表预置业务权限；后续矩阵查看不覆盖显式修改。职位只读，目标人员同级/上级保护独立于可授角色级别。

## 初始业务权限

admin登录后，依次打开普通员工、项目经理、部门经理和公司领导的“配置权限”，切换各业务系统即可查看初始已选项。普通员工94项、项目经理253项、部门经理582项、公司领导466项业务操作，另显式选择这些操作所需的功能/模块祖先菜单。统计不含菜单和RBAC自身操作；原表“无”不授予、I340普通员工空白不授予，view按查看识别。

角色业务权不按职级继承；公司领导不一定能完整授予部门经理，项目经理也可能缺少普通员工的个别操作。候选继续检查全部系统权限子集，不会为方便授予而补权。业务API依旧为空；普通员工无本RBAC管理准入，新建自定义角色仍为空权限。

后续正式实现除上表外还需R27目标保护、R28跨系统完整子集与选权规则；生产OpenAPI24操作及17项完整K尚未调整。本轮不运行Java/数据库/部署验收，不能沿用旧结果声明新规则完成。
